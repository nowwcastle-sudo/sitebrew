## 1. 높음

### F1. `startSite().stop()` 이 서버를 끄지 못한다

`factory/stamp/qa.mjs:162-` 의 `startSite` 는 `stop` 에서 `killTree(child)` 를 부른다. `killTree` 는 **PID 숫자**를 받는데 `child` 객체를 넘긴다. 또 자식을 `detached` 없이 띄워서 Linux 의 `process.kill(-pid)` 도 듣지 않는다.

실측(`startSite` 와 같은 옵션으로 `sleep 30` 을 띄움):
```
killTree(child 객체)            → 자식이 살아 있음
killTree(child.pid), 비분리     → 살아 있음
killTree(child.pid), detached   → 죽음
```
Windows 에서는 `taskkill /PID [object Object]` 가 돼 실패한다(코드 읽기, 실측 아님). 지금 07-qa 가 후보마다 `next start` 를 남길 가능성이 있고, T4 가 `startSite` 를 그대로 쓰면 비교 서버 3개가 그대로 남는다. 반목표 A5(프로세스 잔존 0)가 깨진다.

**고침(T4에 추가)**: `qa.mjs startSite` 를 `detached: !WIN` + `killTree(child.pid)` 로 고친다. `qa.mjs` 는 06 열쇠 밖이다. 시험은 "stop() 뒤 PID가 사라진다"를 Linux 에서 실제 프로세스로 본다. 이 고침은 07-qa 의 기존 누수도 함께 닫는다.

### F2. 남은 서버 정리 규칙이 느슨하다

계획 T4: "남은 pids는 명령줄에 그 run site 경로가 있을 때만 끈다". 막힌 곳 셋:
1. 명령줄을 읽는 방법이 없다. Windows 11 24H2 는 `wmic` 이 없다. `Get-CimInstance Win32_Process` 가 맞다. 한글·공백 경로는 콘솔 코드 페이지에서 깨질 수 있어 대조가 영원히 실패한다.
2. PID 재사용을 막지 못한다. 명령줄에 경로가 있어도, 같은 경로의 다른 `next start`(사용자가 직접 띄운 것)를 끌 수 있다.
3. 탭을 닫거나 부모가 죽으면 자식 3개가 `idleMs`(2시간) 동안 남는다.

**고침(T4에 추가)**:
- `serve.pids.json` 에 `{ pid, port, startedAt, startTime }` 을 적는다. `startTime` 은 OS가 준 프로세스 시작 시각이다(Windows `CreationDate`, Linux `/proc/<pid>/stat`).
- 정리할 때 **PID가 살아 있고 `startTime` 이 같고 명령줄에 siteDir 이 있을 때만** 끈다. 하나라도 읽지 못하면 끄지 않고 한 줄로 알린다(안전한 쪽으로 틀린다). 경로 비교는 `path.resolve` + 소문자(Windows)로 맞추고, 명령줄 읽기는 UTF-16 출력으로 받는다.
- 대시보드가 10초마다 `/__sitebrew/ping` 을 보낸다. **90초 동안 핑이 없으면 서버를 끈다**(탭 닫힘). `idleMs`(2시간)는 핑이 있어도 사용자 입력이 없는 한계로 그대로 둔다.
- 종료 처리: `process.on('exit')` 동기 `killTree`, `SIGINT`·`SIGTERM`·`SIGHUP`. Windows 콘솔 창을 닫는 경우는 처리기가 못 돈다. 그 경우는 다음 `--serve` 의 정리가 맡는다고 SKILL 에 적는다.

### F3. 「계열이 서로 달라야 한다」는 실행 불가능에 가깝다

P1 의 재료 계열 표를 프리셋에 적용해 세었다(실측, `listPresets({archetype})` 결과를 `materialFamily` 규칙으로 분류).

| 원형 | 프리셋 수 | 계열 분포 |

| dashboard | 49 | plain 44 · print 3 · paper 2 |
| public | 43 | plain 39 · editorial 2 · paper 2 |

a 안은 라이브러리 레시피이고 그 60%가 `plain` 이다. 세 후보가 서로 다른 계열이려면 dashboard 는 b·c 가 `print`·`paper` 프리셋 5개 가운데 둘이어야 하고, public 은 `editorial`·`paper` 4개 가운데 둘이어야 한다. 팔레트·린트·다양성 검사를 거치면 후보가 모자라 `DirectionsShortError` 로 끝날 수 있다. 또 `plain` 안에도 서로 아주 다른 것이 많다(dashboard 의 plain 끼리 946쌍 중 673쌍이 `visualDistance ≥ 2`).

**고침(T21 바꿈)**:

- `family-clash` 는 `rejected` 사유가 아니라 후보 `why` 의 경고 문구로만 남긴다.
- **Phase A 에 읽기 전용 점검을 둔다**(새 과제 T0c, 열쇠 밖): 원형 10 × 프리셋·라이브러리 풀에서 계열·거리 분포 표를 만들어 `docs/qa/` 에 둔다. Phase B 에 들어가기 전에 규칙이 실행 가능한지 본다. 이 세션의 `/tmp/feas.mjs` 가 시작점이다(저장소 밖).
- 부록 B 시험 「쌍마다 ≥2 · 계열 3종」은 「쌍마다 ≥2」 하나로 줄이고, 계열 3종은 brand 원형에서만 기대한다.

### F7. 중계·대시보드 서버 보안

CSP 처리 자체는 계획대로 된다. 확인한 것(코드 읽기, `site-template/security-headers.mjs`):
- `frame-ancestors 'none'` 은 `BASE_CSP` 한 줄뿐이다. `X-Frame-Options` 는 싣지 않는다.
- `upgrade-insecure-requests` 는 없다(있으면 `http://127.0.0.1` 하위 자원이 올라가 깨진다).
- `script-src 'self'` 라서 같은 출처의 `/__sitebrew/bridge.js` 는 허용된다. 인라인 스크립트 해시는 `</head>` 앞에 외부 스크립트 태그를 더해도 안 바뀐다.

막힌 곳:
1. **대시보드 서버 `POST /pick`·`/stop`** 에 요청 검증이 없다. 같은 PC 의 아무 웹 페이지가 `fetch('http://127.0.0.1:포트/pick', { mode: 'no-cors', method: 'POST' })` 를 보낼 수 있고, DNS 재바인딩도 가능하다. → 실행마다 `crypto.randomBytes(16)` 토큰을 URL 경로에 넣고(`/c/<토큰>/…`), `Host` 가 `127.0.0.1:<포트>` 인지, `Origin` 이 있으면 대시보드 출처인지 본다. 아니면 403.
2. **postMessage 출처 검증.** 대시보드는 `event.origin ∈ 중계 출처 3개` 이고 `event.source ∈ iframe.contentWindow` 인 것만 받는다. bridge 는 `event.origin === dashboardOrigin`(proxy 가 bridge 소스를 만들 때 값을 박는다)인 것만 받는다. `targetOrigin` 은 `'*'` 가 아니라 상대 출처로 쓴다.
3. **기동 순서.** `frame-ancestors <dashboardOrigin>` 에는 포트가 들어가므로 대시보드 서버가 **먼저** listen 해야 한다. 계획에 순서가 없다.
4. **HTML 재작성의 모서리.** 버퍼링하는 HTML 응답은 `transfer-encoding` 을 지우고 `content-length` 를 새로 잰다. CSP 헤더가 없으면 **더하지 않는다**(늘리지 않는다). 헤더가 배열·여러 줄이어도 각 줄을 처리한다. `Host` 는 요청 그대로 넘긴다(리다이렉트 `Location` 이 중계 포트를 가리키게). 시험 항목에 넣는다: 청크 응답 · 304/HEAD · CSP 없음 · `Location` 상대 경로 · 큰 PNG 바이트 동일.
