# 공장 규칙 (factory rules)

부품·스타일·레시피·블록·원형을 조합해 여러 사이트를 찍어낼 때 적용하는 규칙이다. 코드·시험·문서의 인용(`factory-rules.md §22-1 L3` 같은 모양)이 이 문서의 절과 규칙 ID를 가리킨다.

- **번호는 고정이다.** 절 번호(§20-1 … §23-8)와 규칙 ID(L1 … U21)는 인용이 가리키는 값이라 바꾸지 않는다. 규칙을 더하면 뒤에 번호를 붙인다.
- **이 문서는 §20~§23만 담는다.** 본문과 코드 주석의 「§7」「§13」「§14-D」처럼 20 앞 번호는 타이포·색·접근성·모션 같은 일반 디자인 규칙의 번호이며, 이 저장소에 들어 있지 않다.
- **표기.** `[MUST]`는 어기면 출고하지 않는 규칙, `[SHOULD]`는 이유를 남기면 어길 수 있는 규칙이다. 규칙 끝의 괄호는 규칙 ID와 법령·표준 같은 공개 근거다. 한국 법령 근거는 현행 조문을 확인해 쓴다.

## 20. 공장 규칙 — 조합해서 찍어낼 때의 규칙

한 페이지를 손으로 만들 때는 필요 없던 규칙이다. 부품·스타일·레시피·블록·원형을 조합해 여러 사이트를 찍어낼 때 적용한다. 규칙마다 끝의 괄호에 법령·표준 같은 공개 근거를 적었다.

### 20-1. 원천과 생성물
- [MUST] 사람과 에이전트는 **원천**만 고친다: 레시피 DESIGN.md, 스타일 축 CSS, 원형 JSON, 콘텐츠 객체. 레지스트리 JSON·순수 CSS·페이지·에이전트 안내 파일은 생성기가 만든 **생성물**이라 손으로 고치지 않는다. 같은 값을 두 곳에 적어야 하면 한쪽을 다른 쪽에서 생성한다.

### 20-2. 스타일 축 — 모양은 축 단위로 고른다
- [MUST] 부품의 **모양**(반경·높이·글자 크기·테두리/링 방식·입력 채움·카드 간격)은 shadcn `cn-*` 훅으로만 지정한다. **규칙**(포커스 링 3:1·2px, 히트 영역, 상태 5종, reduced-motion)은 훅 밖 부품 코드에 두어, 스타일을 바꿔도 규칙은 흔들리지 않게 한다.
- [MUST] 모양은 축(버튼 형태·입력 채움·카드/표면·표 밀도·헤더/내비)마다 검증된 값 2~4개 중에서 고르고, 축 사이 조합은 호환표에 있는 것만 쓴다. 반경 계열(0 / 4~12px / 큰 반경)을 섞지 않는다. 부품마다 따로 고르지 않는다.
- [MUST] 새 축 값은 전 부품 × 라이트·다크 × 1440·375 감사와 규칙 lint를 통과해야 호환표에 오른다.
- 예외: 「선 구획」 축 값(선으로 칸을 나누는 스타일)을 고른 레시피는 §6 「구분은 테두리부터 찾지 않는다」의 예외다(선 3:1). 단색 오프셋 그림자는 브루탈(반경 0) 축 값에서만 쓴다.

### 20-3. 레시피
- [MUST] 레시피 하나 = 축 값 조합 1 + 색 3층 토큰(라이트·다크 모두 본문 7:1) + 글꼴 짝 + 아이콘 라이브러리 1 + 모션 강도 1 + 레퍼런스 2개 이상(카드 id 또는 URL). 하나라도 빠지면 레시피가 아니다. 형식은 DESIGN.md 명세(YAML 토큰 + 설명)로 둔다.
- [MUST] 레시피의 모든 글꼴 스택에 한글을 그리는 서체가 있어야 한다. 라틴 전용 디스플레이 서체 뒤에 한글 서체를 둔다.
- [MUST] §13 AI 티 조합은 레시피로 만들지 않는다. 금지 목록(서체·색·배치)은 **데이터 파일**로 두고 분기마다 갱신한다. 서체는 「조정 없는 기본값」만 금지 목록에 올린다(§14-D). (§13)

### 20-4. 원형과 찍어내기 절차
- [MUST] 원형은 고정 페이지가 아니라 데이터다: 목적·핵심 과업·페이지 목록·페이지마다 섹션(필수/선택·중요도·허용 변형·문구 칸·이미지 칸)·전역 섹션·추천 레시피·콘텐츠 스키마·법적 요건. 유형별 규칙은 §21.
- [MUST] 찍어내기 순서: 브리프 → 방향 3안(§1-B) → 사이트맵(원형 JSON 채우기) → 변형 선택 → 콘텐츠 채우기와 윤문(§14-C) → 렌더 → 검수 → 사람의 결선. 앞 단계를 건너뛰고 화면부터 만들지 않는다.
- [MUST] 한 브리프에서 후보를 3개 이상 내고, 후보끼리 레이아웃·스타일·테마 중 두 축 이상이 달라야 한다(첫 화면 실루엣 거리로 잰다).
- [MUST] 연달아 만든 두 사이트는 구조 6축(섹션 제목 배치·본문 구성·구분선·버튼 목소리·이미지 처리·등장 방식) 중 3개 이상, 테마 3축(바탕 명도대 L<30/30~85/>85%·디스플레이 서체 계열·액센트 hue대) 중 1개 이상 달라야 한다. 같은 유형의 직전 산출물과 같은 팔레트 계열·같은 디스플레이 서체를 연달아 쓰지 않는다. 고른 값은 CSS 첫 줄 주석과 생성 로그에 남기고 다음 방향을 고를 때 대조한다.

### 20-5. 콘텐츠 객체
- [MUST] 화면·JSON-LD·llms.txt·에이전트용 폼 속성은 **같은 콘텐츠 객체 하나**에서 만든다. 화면 값과 JSON-LD 값이 어긋나면 불합격.
- [MUST] 이미지 칸마다 출처 정책을 둔다(실사 필수 / 실사 권장 / 생성 허용 / 일러스트). 사람·장소·판매 상품·작업물은 실사 필수다. 공장 예시에는 상업 무료 사진을 쓰고 라이선스 URL을 기록한다. (NN/g)
- [MUST] 3D 오브젝트는 이미지에서 시작한다. 고품질 원본 이미지(판매 대상은 실제 사진, 상징·분위기 오브젝트는 생성 이미지) → 이미지-3D 변환으로 만든 GLB 모델 → 화면은 three.js 로 표시만 한다. 라이브러리 기본 도형(매듭·다면체·고리 등)만으로 3D 장면을 채우지 않는다 — 허접해 보이고 대체도 아니다.
- [MUST] 3D 재료가 없는 사용자를 위한 대체가 있어야 하고, 없으면 왜 안 되는지 알린다. 대체 순서는 모델 없음 → 원본 이미지 + 깊이 시차(2.5D) → 포스터만 → 이 히어로를 고르지 않음이다. 3D 히어로는 모델이나 원본 이미지가 없으면 선택되지 않고, 실행 전 점검(doctor)이 재료가 없다는 사실과 대체 동작을 한 줄로 알린다.
- [MUST] 생성 이미지·모델을 공개 키트에 넣기 전에 생성 도구의 약관(상업 이용·재배포·학습 금지 조항)을 확인한다. 확인 전의 자산은 갤러리 예시 전용으로 표시한다(`docs/qa/factory-v1/asset-licenses.md`).
- [SHOULD] 3D 모델은 2 MB 이하, 텍스처 1024 이하, 첫 칠(LCP)은 포스터 그림이다. three.js 는 첫 화면 이후에 내려받고, 동작 줄이기에서는 내려받지 않는다.
- [SHOULD] 문구 칸마다 역할·최대 글자 수·말투·금지어를 두고, 문구는 페이지 단위로 한 번에 쓴 뒤 윤문한다.

### 20-6. 블록 계약 — 기능 공장과의 접합면
- [MUST] 데이터를 받는 블록은 공통 계약 타입(ActionResult·AsyncState·BlockBase)에만 기대고 서버·SDK를 직접 부르지 않는다. 기능은 어댑터가 계약을 구현해 끼운다(정적·mock·기능 어댑터).
- [MUST] 모든 데이터 블록은 로딩·빈 값·오류·준비·제출 성공·검증 실패·서버 오류를 렌더하고, mock 어댑터로 전부 검사한다.
- [MUST] 되돌릴 수 없는 행위(예약 확정·결제·전송)는 에이전트 자동 제출을 끈다. 에이전트는 채우고 사람이 누른다.

### 20-7. 출고 판정
- [MUST] 판정 순서: ① 결정적 검사 전부 통과(정적·렌더 감사·UX 관문·동작·AI 티 점수·Lighthouse Agentic Browsing·화면↔JSON-LD 대조) ② AI 결함 목록 치명 0 ③ 후보가 5개 이상이면 AI 쌍대 예선(좌우를 바꿔 두 번 같은 답일 때만 인정) ④ **사람의 쌍대 결선** 「이걸 고객에게 그대로 넘기겠나?」. 절대 점수(6.5 등)는 진단 기록으로만 둔다.
- [MUST] AI 예선은 사람이 「확실히 낫다」고 한 쌍에서 일치율 85% 이상일 때만 쓴다. 미달이면 끄고 사람이 후보를 직접 본다. 결선 결과는 쌍 기록(`pairs.jsonl`)에 쌓아 보정에 쓴다.

### 20-8. 갱신
- [MUST] 트렌드·레퍼런스 반영은 파일 교체(스타일 축 CSS·레시피·금지 목록·레퍼런스 샘플)로만 한다. 골든 세트(원형별 브리프 2개) 전체를 다시 생성해 검수와 사람의 결선을 통과해야 태그를 올린다. 생성 모델을 바꿀 때도 같다.
- [SHOULD] 레퍼런스 카드는 사이트 3곳 이상·공급원 2곳 이상에서 관찰된 패턴만 올리고, 카드마다 「보여줄 것 · 값(hex·px) · 가져오지 말 것」을 적는다. 목업 공급원(드리블 등)은 가중 0.2.
- 유행 스타일 승격(design-trend-styles): 새 유행 스타일(리퀴드 글라스류 등)은 레퍼런스 v2 카드 3곳 이상에서 보일 때만 축 값 후보가 된다. 3곳 미만은 `docs/qa/factory-v1/trend-styles.md` 표에 건수만 적고 축 값을 만들지 않는다. 3곳 이상이어도 사람이 보드에서 고른 뒤에 축 값을 만든다.
- [MUST] 약관이 AI 파생물·데이터셋 사용을 금지하는 공급원(Mobbin·Refero)은 카드 출처로 쓰지 않고 사람 확인용으로만 쓴다. 우회 수집은 하지 않는다.

### 20-9. 에이전트 입구
- [SHOULD] 공장 저장소에는 에이전트용 `docs/agents/agent-guide.md`(작업 → 스킬 표), 원형별 과업 파일, 「기본 shadcn과 다르게 동작하는 부품」 목록을 둔다. 공식 shadcn 스킬이 주는 문맥은 다시 적지 않는다.

## 21. 원형별 규칙 — 사이트 유형마다 다른 것

보편 규칙(§1~§20) 위에 원형 하나를 골라 켠다(§20-4). 여기에는 그 유형에서만 맞는 규칙과 유형별 판정만 둔다. 섹션 순서 템플릿·필수/선택 섹션·문구 칸·이미지 칸은 공장 데이터 `registry/factory/archetypes/<id>.json`에 있다.

### 21-1. SaaS 랜딩 (`saas`)
목적: 방문자가 제품이 자기 작업에 맞는지 확인하고 무료 가입(또는 데모 신청)을 시작하게 한다. 핵심 과업: 에이전트가 홈에서 3클릭 안에 요금제별 월 가격을 읽고, 가입 폼 첫 입력란에 닿고, 「○○와 연동되나」에 예·아니오와 근거 URL로 답한다.
- [MUST] 헤더 주 내비에 「요금(Pricing)」 링크를 항상 두어 어느 페이지에서든 한 번 클릭으로 요금 페이지에 닿게 한다. 홈을 겸하는 SaaS 랜딩은 요금표 섹션 대신 이 링크와 마지막 CTA로 요금 페이지를 가리키고, §10 설득 흐름의 「가격」 섹션은 광고·특정 링크로 들어오는 캠페인 랜딩에만 둔다. (NN/g show-price)
- [MUST] 「연동·호환」 섹션을 홈에 하나 둔다: 실제로 연동하는 제품 이름(로고·목록), API·SDK·웹훅 제공 여부, 가져오기 경로. 연동하지 않는 제품의 로고는 쓰지 않는다. (NN/g b2b-vs-b2c)
- [SHOULD] 기능 섹션은 기능 목록이 아니라 사용자의 작업 흐름 순서(예: 접수 → 계획 → 실행 → 배포)로 나눈다. 한 섹션은 한 단계이고, 그 단계의 실제 UI 조각 하나를 보인다.
- [SHOULD] 히어로 CTA는 주 행동 1개(무료 시작·가입)와 보조 1개(데모 보기·영업 문의)로 두고 둘의 크기·채움을 다르게 한다. 세 번째 행동부터는 링크 글자로 낮춘다.
- [SHOULD] 청중을 실사용자(작업 흐름·사용 경험)와 결정권자(보안·규모·지원·계약 조건 — SSO·SLA·인증)로 나눠 보이고 엔터프라이즈 경로를 홈에 둔다. 전환 비용 걱정(기존 도구에서 가져오기·이전 지원·해지 뒤 데이터 반출)에는 FAQ나 요금 근처에서 답한다. (NN/g b2b-vs-b2c)
- [SHOULD] 문서(Docs)·도움말·API 레퍼런스는 로그인 없이 열리고 헤더나 푸터에서 한 번에 닿는다. (NN/g b2b-trust)
- [SHOULD] 「변경 기록·새 기능」 섹션은 날짜 붙은 최신 3~5개만 보이고 전체 변경 기록 페이지로 잇는다. 마지막 항목이 90일 넘게 지났으면 섹션을 뺀다. (§10-A)
- [SHOULD] 1440 폭 기준 히어로 H1 56~72px, 섹션 H2 40~56px, 본문 16~18px. 마지막 CTA 섹션의 H2는 다른 H2보다 한 단계 크게 해 페이지의 마침표로 쓴다.
- [SHOULD] 가격이 공개된 SaaS는 `SoftwareApplication`(또는 `WebApplication`) JSON-LD에 `offers`(가격·통화)·운영체제·범주를 넣고 화면의 요금과 같은 값을 쓴다. 가격이 없으면 `Organization`만 둔다. (Google software-app)
- 섹션 순서 템플릿(제품 주도형·영업 병행형·캠페인)과 문구·이미지 칸: `archetypes/saas.json`.

### 21-2. 브랜드·회사 홈 (`brand`)
목적: 고객·구직자·투자자·기자가 이 회사가 무엇을 하는지 알고 알맞은 곳으로 가게 한다. 핵심 과업: 로그인 없이 3클릭 안에 「이 회사는 무엇을 하나」를 H1이나 첫 문단에서 한 문장으로 답하고, 채용 목록에 닿고, 최근 보도자료의 제목·날짜와 주요 연락처를 읽는다.
- [MUST] 주 내비에 회사 정보 묶음을 직접 둔다: 회사소개·소식(뉴스룸)·채용. 상장사는 투자정보(IR), 지속가능성을 내세우는 회사는 ESG·지속가능성을 더한다. 라벨은 누구나 아는 말로 쓴다(「Corporate Governance」 같은 전문용어 대신). (NN/g 회사 정보 보고서 지침 13)
- [MUST] 회사 정보는 네 층으로 둔다: ① 홈 태그라인(H1) ② 회사소개 페이지 맨 위 1~2문단 요약(하는 일·차별점·주요 성과) ③ 하위 페이지(미션·연혁·리더십·채용·지속가능성) ④ 푸터 링크. (NN/g about-us 4 levels)
- [MUST] 사회·환경 기여를 주장하면 수치와 연도가 붙은 원문 자료(지속가능성·ESG 보고서)를 함께 둔다. 증거 없는 친환경·상생 문구는 쓰지 않는다. (NN/g 지침 43)
- [MUST] 사람·장소·제품 이미지는 실제 촬영물(직원·현장·제품)이다 — 사용자는 스톡을 불신 요인으로 꼽았다. 리더십은 이름·직함·사진·약력을 함께 보인다. (NN/g about-us)
- [SHOULD] 미션·가치 문장은 짧고 구체적으로 첫 두 화면 안에 둔다. 다른 회사 이름을 넣어도 말이 되면 다시 쓴다(§9). (NN/g 지침 30)
- [SHOULD] 제품 브랜드형 홈은 첫 세 화면 안에 라인업(모델·서비스 이름 + 한 줄 설명)을 한 번에 보이고, 제품마다 행동 하나(체험 예약·자세히)를 붙인다. (§10-A)
- [SHOULD] 외부 인정(수상·안전 등급·인증)은 발급 기관·연도와 함께 전용 자리에 둔다. 출처 없는 「No.1」「최고」는 쓰지 않는다. (NN/g 지침 47 · §9)
- [SHOULD] 연혁은 연도별 목록·표(`<ol>`·`<table>`)로 JS 없이 전부 보이게 하고 가로 스크롤 타임라인이나 과한 애니메이션에 가두지 않는다. 회사소개·IR·채용·보도자료 페이지에는 공식 회사명(한국은 상호·법인명)을 글자로 적고 죽은 회사 콘텐츠 링크를 지운다. (NN/g 지침 17 · §8-5)
- 섹션 순서 템플릿(기업 소개형·제품 브랜드형·에디토리얼형)과 문구·이미지 칸: `archetypes/brand.json`.

### 21-3. 동네 가게·예약 (`local`)
목적: 손님이 「지금 여는가·어디인가·어떻게 예약하나」를 바로 알고 예약·전화·방문하게 한다. 핵심 과업: 390×844에서 스크롤 없이 오늘 영업시간과 주소를 읽고, 예약(또는 전화) 버튼으로 예약 채널 URL(또는 `tel:`)에 닿고, 두 화면 안에서 네이버 지도·카카오맵 링크를 찾는다(답이 JSON-LD와 일치).
- [MUST] 모바일(390px) 첫 화면이 오늘 영업시간(휴무면 「오늘 휴무」)·주소 한 줄·주 행동 버튼 하나(예약 또는 전화)를 보인다. 영업시간·주소를 푸터나 「Contact」 페이지에만 두지 않는다.
- [MUST] 예약 경로는 가게가 실제로 받는 채널 하나(네이버 예약·캐치테이블·카카오톡 채널·전화 중 하나)를 주 CTA로 정하고 나머지는 보조 링크로 낮춘다. 모바일에서는 주 CTA를 하단 고정 바에 둔다.
- [MUST] 메뉴·가격표·시술/진료 가격은 HTML 텍스트로 싣는다. 메뉴판 사진·PDF는 보조로만 두고, PDF는 쪽수·용량을 적은 HTML 안내 뒤에 링크한다. (NN/g avoid-pdf)
- [MUST] 오시는 길: 복사할 수 있는 텍스트 주소, 네이버 지도·카카오맵 길찾기 링크, 대중교통 한 줄, 주차 여부. 외국인 손님을 받으면 영문 주소와 구글 지도 링크를 더한다. 지도 iframe만으로 위치를 알리지 않는다. (§9 · §10-A)
- [MUST] 파는 메뉴·상품, 실제 공간, 의료진은 실사만 쓴다(생성 이미지 금지 — §6-A 단서). 사진이 없으면 비율을 고정한 빈 슬롯(「매장 사진 자리」)으로 납품하고 사장님 사진을 받는다. 생성 이미지는 판매 대상이 아닌 분위기 컷에만 표기와 함께 쓴다. (§14-B)
- [MUST] **의료 변형**(병원·의원·치과·한의원)은 치료경험담 후기를 싣지 않고 후기 칸을 끈다(§9 후기 규칙의 예외, 의료법 제56조②2). 전후 사진, 다른 의료기관과의 비교, 근거 없는 인증·수상 배지, 심의받지 않은 광고 문구도 싣지 않고(같은 조 ②4·8·14, 시행령 제23조) 진료 정보로 신뢰를 만든다. (의료법 제56조 · 시행령 제23조)
- [SHOULD] 의료 변형의 홈은 심의 없이 알릴 수 있는 사실로 채운다: 명칭·소재지·전화·진료과목·의료인 성명·성별·면허 종류, 진료시간표(점심시간·야간·주말·휴진일). (의료법 제57조 심의 제외 항목)
- [SHOULD] 임시 휴무·브레이크타임·품절 공지는 첫 화면의 날짜 붙은 한 줄 공지로 싣는다. 진입 팝업 레이어로만 알리지 않는다(§7-B).
- [SHOULD] 지점이 2곳 이상이면 지점 카드마다 같은 형식(지점명·주소·오늘 시간·전화·지도 링크)과 지점별 URL을 둔다. 구조화 데이터는 가장 구체적인 하위 유형(Bakery·CafeOrCoffeeShop·Restaurant·Dentist·MedicalClinic·HairSalon 등)으로 지점마다 따로 쓴다: 필수 `address`·`name`, 권장 `openingHoursSpecification`·`telephone`(국가번호 포함)·`geo`(소수점 5자리 이상)·`url`, 음식점은 `menu`·`servesCuisine`, 모두 화면 값과 같게. (Google LocalBusiness)
- 섹션 순서 템플릿(바로 찾기형·의료 신뢰형·예약 상품형)과 문구·이미지 칸: `archetypes/local.json`.

### 21-4. 포트폴리오·스튜디오 (`portfolio`)
목적: 의뢰인이 실제 작업을 보고 역량을 판단해 프로젝트를 문의하게 한다. 핵심 과업: 특정 분야 작업 3개의 제목·의뢰인을 나열하고(JS를 끈 상태에서도), 그중 하나의 사례 페이지를 고유 URL로 열어 결과를 두 문장으로 요약하고, 새 프로젝트 문의 이메일 주소를 돌려준다.
- [MUST] 홈에서 첫 작업(썸네일 + 제목 + 의뢰인)이 두 화면 안에 보인다. 소개 선언문은 한 화면 안에 끝낸다. (NN/g ux-design-portfolios)
- [MUST] 사례 페이지 순서: 맨 위 메타(의뢰인·제공 서비스·연도·역할) → 과제 → 역할과 협업 → 과정(버린 안 포함) → 해결 → 결과(수치·수상·의뢰인 말) → 다음 작업 링크. (NN/g)
- [MUST] 작업 이미지·영상은 모두 실제 작업물(납품 결과·현장 사진·과정 스케치)이다. 생성 이미지나 기기 목업만으로 작업을 대신하지 않고, 비공개 작업은 과정 자료(흑백 와이어·스케치)로 보인다. (NN/g ux-design-portfolios)
- [MUST] WebGL·캔버스 갤러리를 써도 모든 작업을 DOM 안의 진짜 `<a href>` 목록과 고유 URL(`/work/<slug>`)로 한 번 더 준다. 캔버스는 그 목록을 꾸미는 층이다. (§12 · §10-B)
- [SHOULD] 사례 본문은 짧은 글 덩어리와 이미지를 번갈아 둔다 — 연속 본문 약 150단어(한글 약 400자)마다 figure 하나. (NN/g)
- [SHOULD] 주 내비는 작업(Work)·소개(About/Info)·연락(Contact)을 필수로 5개 이하. 작업이 많으면 분야별 필터나 묶음(브랜드·모션·디지털 등)을 두고 필터 상태를 URL에 남긴다. (NN/g · §10-B)
- [SHOULD] 홈 마지막은 협업 제안 CTA(「프로젝트 문의」)이고, 그 옆과 푸터에 실제 이메일 주소를 글자로(`mailto:`) 둔다. 폼만 두지 않는다. 고객 명단·수상·언론 노출은 이름·연도와 함께 글자로 쓴다(수상 배지 이미지만 두지 않는다). (§9)
- [SHOULD] 작업 이미지가 위계를 맡는 격자형 홈에서는 UI 글자(내비·작업 제목·라벨)를 16~19px 한 크기로 통일하고, 큰 글자는 선언문 H1(42~72px) 한 곳에만 쓴다. 라벨도 14px 아래로 내리지 않는다.
- 섹션 순서 템플릿(작업 격자형·선언 + 선별형·사례 페이지)과 문구·이미지 칸: `archetypes/portfolio.json`.

### 21-5. 소형 커머스 (`commerce`)
목적: 손님이 상품을 찾아 옵션을 고르고 배송비를 포함한 합계를 확인한 뒤 산다. 핵심 과업: 홈 → 카테고리 → 상품 → 옵션 선택 → 장바구니 담기 → 배송비를 포함한 합계 읽기(결제는 누르지 않는다), 이어서 푸터에서 사업자등록번호·통신판매업 신고번호를 읽고 공정위 조회 링크가 열리는지 확인한다.
- [MUST] 선지급식(무통장입금 포함)으로 팔면 결제대금예치(에스크로) 또는 소비자피해보상보험을 고를 수 있다는 문구를 결제 수단 근처와 푸터에 보인다(전자상거래법 제13조②10). 무통장입금 계좌는 은행·계좌번호·예금주를 함께 적는다. (전자상거래법 제13조)
- [MUST] 사이즈·색 옵션은 드롭다운이 아니라 보이는 버튼으로 고르게 하고, 품절 옵션은 「품절」 글자를 붙여 보인다(흐리게만 하지 않는다). §7-A의 SHOULD를 커머스에서는 MUST로 올린다. (Baymard 57% Don't · §7-A)
- [MUST] 파는 상품은 실물 촬영만 쓴다(생성 이미지 금지 — §6-A 단서). 누끼·배경 확장은 상품의 모양·색을 바꾸지 않는 선에서만 쓰고, 생성 이미지는 상품이 들어가지 않은 분위기·계절 배너에만 표기와 함께 쓴다. (§14-B)
- [SHOULD] 용량·수량이 다른 상품(원두·식품·생활용품)은 가격 옆에 단위 가격(「100g당 3,200원」)을 보인다. 찜은 로그인 없이 되고 로그인하면 합친다. 선물 수요가 있으면 선물 포장·메시지 옵션(카카오톡 선물하기에 입점했다면 그 경로)을 상세에서 보인다. (Baymard current-state 81%)
- [SHOULD] 낮은 별점 리뷰에 판매자 답글을 날짜와 함께 단다. (Baymard 89% Don't)
- [SHOULD] 식품을 팔면 원산지 안내를 상시 메뉴나 상세의 고정 자리에 둔다.
- [SHOULD] 모바일 웹 커머스는 하단 5탭 바를 기본으로 두지 않는다(§14-A 유지 — 근거가 관찰 1곳뿐). 설치해 쓰는 앱형이면 `pwa` 원형(§21-9)을 함께 켜고 그 탭바 규칙을 따른다.
- 섹션 순서 템플릿(브랜드 몰·동네 가게 온라인 주문·단일 품목 D2C)과 문구·이미지 칸: `archetypes/commerce.json`. 상품 상세는 §21-6을 함께 켠다.

### 21-6. 상세페이지 — 한국 커머스 (`detail`)
목적: 모바일 상세 한 장에서 구매 판단에 필요한 정보(가격·배송·반품·고시·리뷰)를 글자로 주고, 구매 바에서 바로 옵션을 고르게 한다. 핵심 과업: 390×844에서 ① 배송비와 무료배송 기준 ② 반품 배송비 부담 주체 ③ 제조국 ④ A/S 연락처를 DOM 텍스트로 찾고(이미지 OCR 금지), ⑤ 하단 고정 구매 바로 옵션 시트를 열어 옵션 하나를 고른다(결제는 누르지 않는다).
- [MUST] 상품정보제공 고시의 품목별 항목(제조자·수입자, 제조국, 품질보증기준, A/S 책임자와 전화번호, KC 인증 대상이면 인증정보)을 HTML 표로 싣는다. 이미지 속 글자로만 두지 않는다.
- [MUST] 상세 문구(구매 포인트·스펙·주의사항·배송 안내)는 HTML 텍스트로 싣고, 이미지는 높이 1,000~1,200px 조각으로 나눈다. 세로 수천 px 통이미지에 글자를 굽지 않고, 글자가 든 조각은 alt에 그 문구를 옮긴다. (WCAG 1.4.5 · §12)
- [MUST] 콘텐츠 열은 모바일 기준 최대 폭 860px(스마트스토어 권장)로 짠다. 이미지에 글자를 넣어야 하면 860px 원본에서 본문 36px·제목 54px 이상(390px 화면에서 약 16px·24px — §2 16px에서 역산한 값), 한 줄 15자 이내. (§2)
- [MUST] 모바일 상세에는 하단 고정 구매 바(구매하기·장바구니)를 두고, 누르면 옵션 시트가 아래에서 열린다. 카카오톡 채널 버튼과 겹치지 않게 둔다(§17).
- [MUST] 긴 상세는 펼친 섹션 위의 고정 목차(상세정보·상품정보·리뷰·문의 앵커)로 이동하게 한다. 누르면 내용이 갈아 끼워지는 가로 탭 안에 핵심 내용을 숨기지 않는다. 모바일에서 아주 길면 접힌 섹션을 쓴다. (Baymard avoid-horizontal-tabs 29% Don't)
- [MUST] 제품 컷은 실물 촬영만 쓴다(색·질감·크기가 실제와 같게 — §6-A 단서). 도식·아이콘·설명 그래픽은 제작해도 되고, 생성 이미지는 제품이 없는 배경·분위기 조각에만 표기와 함께 쓴다. 후기 사진은 작성자 동의 범위 안에서만 재사용한다.
- [SHOULD] 섹션 순서는 구매 영역 → 핵심 구매 포인트 → 상세(문제 → 해결 → 근거 → 사용 장면) → 스펙·상품정보제공고시 → 배송·교환·반품 → 리뷰 → 문의를 기본으로 하고, 바꾸면 이유를 결정 기록에 남긴다. 핵심 내용은 모바일 스크롤 10~15회(이미지 조각 8~12개) 안에 끝내고, 긴 설명을 접는 플랫폼(스마트스토어)에서는 구매 포인트를 맨 위에 둔다.
- [SHOULD] 사진 구성: 목록용 이미지는 1:1·1,000px 이상에 상품이 잘리지 않게, 몇 장에는 짧은 설명과 지시선(기능 콜아웃)을 HTML 캡션이나 겹친 HTML로, 크기를 알 수 있는 비교 사진(손·일상 물건·사람과 함께) 1장 이상, 착용·사용 상품은 모델 컷 1장 이상. (Baymard descriptive-text 52%)
- [SHOULD] 리뷰는 포토리뷰를 먼저 모아 보이고, 리뷰 사진에서 리뷰 본문으로 오갈 수 있게 한다. (Baymard 63% Don't)
- 섹션 순서 템플릿(한국 상세 표준·짧은 소모품형·텍스트 중심형)과 문구·이미지 칸: `archetypes/detail.json`.

### 21-7. 운영 대시보드 (`dashboard`)
목적: 운영자가 오늘 할 조치를 놓치지 않고 그 자리에서 처리하게 한다(§1-A). 핵심 과업: 경고 1건을 찾아 레코드 상세를 열고 조치(배정·상태 변경)를 끝낸 뒤 목록의 상태 변화를 DOM으로 확인한다(클릭 3회 이하). 기간을 「지난 7일」로 바꾸고 새로고침해도 조건이 남고, 행 3개 일괄 작업 뒤 「3개 선택됨」과 `role="status"` 결과 알림이 보인다.
- [MUST] 착수 전에 종류를 하나로 정해 결정 기록에 쓴다: **운영**(지금 조치할 것을 알린다) · **분석**(원인을 찾는다) · **전략**(목표 대비 방향을 본다). 셋을 한 화면에 섞지 않고, 갱신 주기는 데이터가 바뀌는 속도가 아니라 사람이 조치할 수 있는 주기에 맞춘다. (NN/g dashboards-preattentive)
- [MUST] 운영형의 조치 영역(1순위)과 기준 시각은 1440×900 첫 화면 안에 스크롤 없이 든다. 분석형은 스크롤·탭을 허용하되 서로 비교할 차트끼리는 한 화면에 둔다.
- [MUST] 모든 KPI·상태 값에 판단 기준(목표값·정상 범위·비교 기간 중 하나 이상)을 붙인다. 기준을 정할 수 없는 숫자는 대시보드에서 뺀다.
- [MUST] 경고색(빨강·주황)과 배지는 지금 조치가 필요한 항목에만 쓴다. 정상 항목을 하나하나 초록으로 칠하지 않고, 경보 조건은 보수적으로 잡는다. (KRDS 색상)
- [MUST] 자동 갱신 화면에는 「갱신 멈춤」 컨트롤을 둔다. 새 데이터가 사용자가 보고 있거나 선택한 행을 밀어내지 않게, 새 항목은 「새 항목 n건 — 보기」로 모아 알린다. (WCAG 2.2.2 · §11 CLS)
- [MUST] 사이드바의 기본 상태는 펼침이다. 접은 상태에서도 항목마다 접근 가능한 이름과 포커스·호버 툴팁이 있고, 아이콘만 남긴 축소를 기본값으로 두지 않는다. (NN/g vertical-nav)
- [MUST] 조밀한 표 행·아이콘 버튼의 히트 영역은 `(pointer: fine)`에서 최소 24×24px로 두고, 터치(`pointer: coarse`)에서는 §7의 44px를 유지한다(§7 예외). (Carbon data table · WCAG 2.5.8)
- [SHOULD] 앱 셸은 왼쪽 세로 사이드바(텍스트 라벨 상시, 접힘 토글 선택) + 상단 바(전역 검색·알림·계정)다. 경고 항목마다 조치 링크(레코드 열기·배정·연락)를 붙이되, 판단이 필요한 조치를 자동으로 대신 실행하지 않는다. (NN/g vertical-nav)
- [SHOULD] 데이터 표의 첫 열은 사람이 읽는 식별자(이름·주문번호), 열은 사용자에게 중요한 순으로 관련 열끼리 붙이고, 열 숨기기·순서 바꾸기는 드래그 없이도 된다. 행 높이는 조밀 32px · 기본 40px · 여유 48px · 두 줄 64px 중에서 고르고(초조밀 24px는 읽기 전용 표만) 헤더 행을 본문 행과 같은 높이로, 한 화면 안에서 섞지 않는다. (NN/g data-tables · Carbon)
- [SHOULD] 일괄 작업은 행 체크박스 + 「n개 선택됨」 + 선택 시 나타나는 표 위 작업 막대 + 전체 선택으로 만든다. 행 안 인라인 작업은 1~2개까지, 그 이상은 이름 붙은 메뉴로 묶는다. 행 상세·편집은 표를 계속 볼 수 있게 오른쪽 비모달 패널로 열고, 모달은 짧은 확인에만 쓴다. (NN/g data-tables · Carbon · §7-B)
- 화면 순서 템플릿(운영형·분석형·관리형)과 KPI·표 칸: `archetypes/dashboard.json`. 사진 칸은 없다.

### 21-8. 공공기관 (`public`)
목적: 국민이 목적별로 필요한 민원·정보에 빨리 닿게 한다. KRDS(범정부 UI/UX 디자인 시스템)를 우선하되 14px 바닥은 지킨다. 핵심 과업: 메인에서 주요 민원 서비스까지 3클릭 이내, 글자 크기 130%에서 같은 과업(가로 스크롤 0), 긴급 공지 링크를 따라가 상세 제목 일치 확인, 키보드만으로 본문 바로가기 → 공식 배너 → 로고 → 푸터 「개인정보 처리방침」까지.
- [MUST] 타이포는 KRDS를 따른다: 행간 150%, 큰 제목 자간은 KRDS 토큰(display 60/44/36px·heading xlarge 40·large 32에 +1px), 서체는 국·영문 모두 Pretendard GOV 한 가족(굵기 400·700, 필요시 500 — 자체 서체는 디스플레이·배너에만, 확장형은 고딕 계열). §2 행간·자간과 §14-D 디스플레이 서체 규칙 대신 이것을 쓴다. 단 §2의 14px 바닥은 유지해 KRDS body xsmall 13px은 쓰지 않는다. (KRDS 타이포 · §2)
- [SHOULD] 착수 전에 기관 유형(중앙행정기관 본부 / 중앙행정기관 운영서비스·시스템 / 공공기관 / 지방자치단체)을 판정해 KRDS 적용 수준(표준형·확장형, 공식 배너·운영기관 식별자 필수 여부)을 결정 기록 맨 위에 쓴다. (KRDS 이용 안내)
- [MUST] 공식 정부 서비스는 모든 화면 최상단(건너뛰기 링크 바로 다음)에 공식 배너 「이 누리집은 대한민국 공식 전자정부 누리집입니다.」를 같은 위치·같은 문구·같은 스타일로 두고, 헤더의 내비·기능 버튼보다 눈에 띄지 않게 한다. 공식 정부 서비스가 아니면 배너를 쓰지 않는다. (KRDS 공식 배너 · USWDS banner)
- [MUST] 헤더 순서: 건너뛰기 링크 → 공식 배너 → 로고(왼쪽 위) → 유틸리티 링크(오른쪽 위, 디바이더로 구분, 5개 이상이면 드롭다운) → 검색 → 메인 메뉴. 헤더를 고정하면 공식 배너는 빼고 고정하고, 2행을 넘는 헤더는 스크롤을 올릴 때만 보인다. 헤더 아이콘 버튼엔 보이는 레이블을 붙이고(검색·로그인만 예외) 로고 alt는 「로고」 없이 기관명만 쓴다(SHOULD). (KRDS 헤더 · GOV.UK page template)
- [MUST] 헤더 유틸리티에 글자 크기 조정을 둔다: 옵션 5개 이내(예: 90·100·110·130%), 배율 숫자와 설명 레이블을 함께. 조정해도 콘텐츠가 가려지거나 기능이 사라지지 않는다. 선명한 화면 모드(고대비)를 두면 본문 15:1, 제목·레이블·아이콘 7:1, 보조 시각 요소 4.5:1을 채운다(SHOULD). (KRDS 화면 크기 조정)
- [MUST] 긴급 공지(재난·장애·중단 예고)는 메인 메뉴와 히어로 사이, 본문 첫 요소로 전체 폭에 **하나만** 둔다: 긴급도 레이블(상·중·하)+아이콘, 문장 1줄(좁은 화면 2줄까지), 관련 화면 링크 1개. 숨기기 버튼을 두지 않고 기간이 끝나면 내린다. (KRDS 긴급 공지)
- [MUST] 메인은 제공자 순서가 아니라 이용 데이터 순서로 짠다. 첫 화면 안에 방문 목적별·사용자 유형별 바로가기(「자주 찾는 서비스」)를 두고, 같은 목적의 콘텐츠는 제목과 한 줄 안내가 있는 한 섹션으로 모은다. 캐러셀은 자동 회전하지 않는다(§7 유지 — 기관이 요구할 때만 KRDS 조건: 정지 버튼이 캐러셀 안 첫 Tab, 포커스·마우스 올림에 정지). (KRDS 방문 패턴)
- [MUST] 목록·링크에는 최신 업데이트·기한 레이블, 짧은 설명, 외부 사이트 표시를, 게시물에는 날짜와 담당 부서를 붙인다. 메인에 보이는 정보의 정기 점검 주기를 운영 문서에 적는다. (KRDS 방문 패턴 · §10-A)
- [MUST] 푸터 순서: 서비스 로고 → 연락처(주소·주 전화·민원전화, 유료 여부·운영 시간) → 유틸리티 링크(오시는 길·관련 기관·소셜) → 정책 링크 → 저작권 → 운영기관 식별자(마지막 구획), 좁은 화면에서도 이 순서. 「개인정보 처리방침」은 이 명칭 그대로 굵기·색으로 다른 고지와 구분하고 웹 접근성 정책 링크를 함께 둔다. 푸터 사이트 내비를 두면 메인 메뉴 최상위를 같은 레이블로 모두 담는다(SHOULD). (KRDS 푸터 · USWDS identifier)
- [SHOULD] 레이아웃 토큰은 KRDS 표준형: 브레이크포인트 360·768·1024·1280px, 칼럼 4·8·12·12, 거터 16·16·24·24px, 최소 스크린 마진 16·24·24·24px, 콘텐츠 최대 1200px. 서브 페이지(1024px 이상)는 헤더 → 브레드크럼 → [왼쪽 사이드 메뉴 · 본문(h1) · 오른쪽 콘텐츠 내 탐색] → 푸터, 간격은 헤더–브레드크럼 24px, 사이드 메뉴–본문 64px, 브레드크럼–h1 40px(모바일 32), 본문–푸터 64px(모바일 40). (KRDS 레이아웃 · §3)
- [SHOULD] 강조색(새 알림·중요 배지)은 주 색(약 10%)과 별개로 면적 5% 이하로 쓴다. (KRDS 색상)
- 화면 순서 템플릿(정책·안내형·업무 개인화형·검색 중심형·서브 페이지)과 칸: `archetypes/public.json`.

### 21-9. 모바일 PWA (`pwa`)
목적: 설치해 앱처럼 쓰는 사용자가 연결이 불안정해도 핵심 과업을 끝낸다. 핵심 과업: 설치 가능 판정(manifest 경고 0, 서비스 워커 등록, 첫 로드에 설치 배너·권한 요청 0), 네트워크를 끊고 홈·최근 화면 열기(미캐시 경로는 사용자 지정 오프라인 화면), 오프라인 작업 1건 저장 → 재연결 → 동기화 완료 표시, standalone에서 하위 화면 → 앱 안 뒤로가기로 복귀.
- [MUST] Web App Manifest에 `name`·`short_name`·`icons`(192px·512px 필수, 마스크 가능 아이콘 포함, 플랫폼 중립 모양)·`start_url`·`display`(`standalone` 기본)·`theme_color`·`background_color`를 채우고 `prefer_related_applications`는 없거나 false로 둔다. `description`과 실제 화면 `screenshots`를 넣으면 Android 설치 창이 앱스토어형으로 커진다. (web.dev installation-prompt)
- [MUST] 최상위 목적지가 3~5개면 하단 탭바를 쓴다(§14-A의 pwa 예외): 아이콘+라벨(1~2단어, 줄바꿈·말줄임·축소 없음), 같은 폭, 위치 고정, 스크롤할 때 숨기지 않음, 홈은 맨 왼쪽·「전체」는 맨 오른쪽. 5개를 넘으면 전체 메뉴로 보내고 3개 미만이면 탭바 대신 상단 탭. 하위 화면에서는 숨겨도 된다. (KRDS 탭바 · M3 navigation bar · Apple HIG tab bars)
- [MUST] 탭바는 이동 전용이다: 가운데 「+」 같은 행동 버튼을 넣지 않고, 떠 있는 주 행동 버튼(FAB)은 탭바 위 오른쪽에 두어 가리지 않는다. 탭바는 키보드·시트·대화상자에 잠시 가려질 수 있지만 영구히 가려지지 않는다. 내용이 없는 탭도 숨기거나 비활성하지 않고 비어 있는 이유를 설명하며, 탭 배지는 중요한 새 정보에만 쓴다(SHOULD). (Apple HIG tab bars · M3 navigation bar)
- [MUST] standalone에는 브라우저 뒤로가기가 없으므로 하위 화면 헤더 왼쪽에 뒤로가기 버튼을 둔다(`@media (display-mode: standalone)`에서 표시). 앱형 헤더의 왼쪽 항목은 3개 이하, 유틸리티 링크는 설정 화면으로 옮긴다. (web.dev app-design · KRDS 헤더)
- [MUST] 설치 유도는 `beforeinstallprompt`가 발생한 뒤에만 보이고, 로그인·결제 폼 밖(메뉴 아래쪽·핵심 여정 완료 직후)에 두며, 닫을 수 있고 거절을 기억한다. 다시 보이는 것은 관계가 바뀐 뒤(로그인·구매 완료)뿐이다. 이벤트가 없는 iOS용 설치 방법 안내는 `display-mode: browser`일 때만 보인다. (web.dev promote-install)
- [MUST] 브라우저 기본 오프라인 화면 대신 사용자 지정 오프라인 화면(재시도 버튼 + 연결되면 자동 재시도)을 캐시한다. 캐시된 화면은 오프라인에서도 열리고, 연결이 필요한 행동만 이유를 말하며 막는다(회색 처리만으로 알리지 않는다). 오프라인 중 작업은 「저장됨 · 연결되면 보냅니다」로 확인해 준다. (web.dev pwa-checklist)
- [MUST] 앱 셸(헤더·탭바·레이아웃)은 캐시에서 먼저 그리고 데이터는 스켈레톤으로 채운다. 재방문 때 네트워크를 기다리는 빈 화면이 없다. (web.dev pwa-checklist)
- [SHOULD] 연결 상태 문구는 「오프라인」 같은 기술 용어 대신 행동 언어로 쓰고 문제가 어느 쪽인지 밝힌다(「인터넷 연결이 끊겼어요」와 「서비스를 점검하고 있어요」를 구분), 같은 문구를 모든 곳에서 쓴다. 첫 로드 뒤 오프라인 준비가 끝나면 짧게 알리고, 큰 콘텐츠는 사용자가 켠 경우에만 미리 받아 「오프라인 저장」 토글과 저장 위치·용량을 설정 화면에 보인다. (web.dev offline-ux-design-guidelines)
- [SHOULD] 서비스 워커가 새 버전을 받으면 「새 버전이 있어요 — 새로고침」 토스트로 알린다. 작성 중인 입력을 날리는 강제 새로고침을 하지 않고 다음 화면 이동 때 적용한다. (web.dev offline-ux-design-guidelines)
- [SHOULD] `user-select: none`은 버튼·탭 같은 UI 컨트롤에만 쓰고 본문은 복사할 수 있게 둔다. `overscroll-behavior-y: contain`은 자체 당겨서 새로고침을 구현할 때만 쓴다. (web.dev app-design)
- 화면 흐름 템플릿(탭 앱형·단일 과업형·오프라인 우선)과 칸: `archetypes/pwa.json`.

## 22. 전환·유지·신뢰 — 마케팅 UI/UX·AX

**규칙 ID.** 규칙 앞머리 글자는 영역을 뜻한다: L 법 바닥선 · P 가격·페이월 · O 가입·온보딩 · R 유지 · T 신뢰 · A 획득 · V 추천 · X AX · M 계측.

**근거 순위.**
1. 한국 법 1차 출처(바닥선)
2. 통제 실험·대규모 측정
3. 플랫폼 규정
4. 여러 독립 스킬의 공통 권고
5. 업체 자체 데이터

해외 CRO 관행이 한국 법보다 느슨하면 한국 기준을 따른다. 커머스 목록·결제는 §15를, 소셜 로그인·카카오 공유 규격은 §17을 그대로 쓴다.

### 22-1. 법 바닥선 (전자상거래법 다크패턴 6유형 2025-02-14 시행 · 방통위 · 공정위)
- [MUST] **필수 총액을 처음부터 보인다.** 가격이 처음 나오는 화면(목록·배너·요금 카드 포함)에 필수 총액(VAT·배송비·필수 수수료)을 보인다. (L1 · §21-2①1)
  - 금액을 정할 수 없는 항목은 이름과 이유를 같은 화면이나 바로 연결된 창에 적는다.
  - 원화는 「VAT 포함」이 기본이다. B2B가 부가세를 따로 적으면 모든 화면에서 「부가세 별도」로 일관되게 쓴다.
- [MUST] 추가 상품·선택 동의 체크박스는 기본 해제로 둔다. 선택 동의(마케팅 이메일·문자·카카오·푸시)는 필수 동의(약관·개인정보)와 분리한다. (L2·L12)
- [MUST] 구매·가입·동의·해지 대화상자의 두 선택지는 크기·대비·위치가 대등해야 한다. 거절 문구는 담백하게 쓴다(「해지하기」). 수치심을 주는 문구는 금지한다(「아니요, 혜택을 포기할게요」). (L3)
- [MUST] **해지는 가입보다 단계가 많지 않다.** (L4·L5)
  - 사유는 선택 1문항으로 묻는다.
  - 대안은 1화면에 하나만 보인다. 순서는 일시정지 → 다운그레이드 → 할인이다.
  - 모든 단계에 같은 무게의 해지 버튼을 둔다. 완료 화면에는 종료일을 적는다.
  - 혜택 반복 강조·만류 질문·다른 상품 권유를 늘어놓지 않는다(방통위 「해지 복잡화」).
  - 약관에 중도해지가 있으면 중도해지와 일반해지를 둘 다 구매·해지·FAQ 화면에 안내한다.
- [MUST] 무료→유료 전환·가격 인상은 **명시 동의** 모달로 받는다. 모달은 청구 30일 전 안에 띄우고, 전후 가격·날짜·해지 버튼을 담는다. 닫기·무응답은 동의가 아니다. (L6)
- [MUST] 거절한 선택을 다시 묻는 창에는 「7일간 보지 않기」와 실제 거절 버튼을 둔다. (L7)
- [MUST] 카운트다운·「N개 남음」·「N명이 보는 중」은 실제 값(블록 prop `endsAt`·재고 데이터)에 묶는다. 되돌아가는 타이머와 상시 「곧 종료」는 금지한다. (L8)
- [MUST] 선불 통신판매는 결제수단 근처에 결제대금예치(에스크로)를 고를 수 있다고 알린다. 앱 안 계정 화면에 구독 관리(요금제·다음 결제일·금액·변경·해지)를 둔다. (L10·L11)

### 22-2. 가격·페이월
- [MUST] **실제 청구액이 가장 크다.** 월 환산가·절감률·「무료 체험」 문구는 보조 크기로 쓴다. (P1 · Apple 3.1.2)
- [MUST] 체험을 시작하기 전 같은 화면에 기간·첫 청구 금액과 날짜·자동 갱신·해지 방법을 보이고, 약관·개인정보 링크를 둔다. (P2)
- [MUST] 요금은 텍스트로 쓰고 통화·주기·VAT를 밝힌다. 비교표는 `<table>`·`<th scope>`로 만든다. 추천은 색만이 아니라 텍스트 배지로 표시한다. 모든 요금제를 「문의」로 두지 않는다(최소한 시작가를 공개). (P3·P11)
- [SHOULD] 실제로 파는 요금제 3단에 추천 배지를 단다. 모든 요금제 CTA는 같은 크기로 둔다. 살 수 없는 미끼 요금제와 5개 이상 요금제는 쓰지 않는다. 월/연 토글은 연 총액과 절감액을 금액으로 보인다. (P4·P5)
- [SHOULD] **업그레이드 제안의 시점과 빈도.** (P6~P10)
  - 가치를 경험한 뒤나 실제 한도에서 제안한다.
  - 사용량 80%에서 인라인 제안을 1회 보이고, 100%에서는 부드럽게 막는다. 무료로 계속할 길은 남긴다.
  - 첫 세션 온보딩 끝의 체험 제안은 「무료로 계속」을 보이게 두면 허용한다.
  - 세션당 노출 횟수를 제한하고, 사용자가 닫으면 며칠 쉰다.
  - 체험 종료 7·3·1일 전에 예고하고, 그동안 만든 가치를 요약한다.
  - 결제 직후 즉시 열어 주고, 새로 열린 기능을 안내한다.
- [SHOULD] 신규 고객을 할인으로 얻지 않는다. 보증·세팅 대행·보너스로 제안을 감싼다. (P12)
- [SHOULD] 요금제 한도는 배수(「5×」)가 아니라 구체 수치로 적는다(월 N건·N GB). 한도를 흐리게 바꾸면 반발이 온다. (P14)

### 22-3. 가입·활성화·온보딩
- [MUST] **가입은 시작에 필요한 필드만 받는다.** 회사·역할·전화는 나중에 묻고, 전화를 받으면 이유를 적는다. (O1·O2)
  - 라벨은 항상 보인다. 검증은 필드를 떠날 때 한다.
  - 오류 문구는 「무엇이 잘못됐고 어떻게 고치나」로 쓴다. 입력값은 유지하고, 제출 시 첫 오류 필드로 포커스를 옮긴다.
  - 필수·선택을 둘 다 표기한다.
- [MUST] 빈 상태에는 이 영역이 무엇인지, 왜 비었는지, 주 행동 하나를 보인다. 샘플 데이터·템플릿은 선택이다. (O7)
- [SHOULD] 첫 가치까지의 단계를 세고 줄인다. 첫 세션이 실제 결과로 끝나게 하고, 첫 가치 전에 필수 프로필을 받지 않는다. 환영 질문은 1개만 묻고, 답에 따라 다음 화면이 바뀌게 한다. (O5·O9)
- [SHOULD] 체크리스트는 3~5개로 만든다(가치 순서·진행률·닫기 가능). 실제로 끝낸 단계만 미리 체크한다. 첫 실행 튜토리얼 카드 대신 처음 쓰는 순간에 맥락 도움말을 보인다. 투어가 필요하면 4단계 이하로, 사용자가 시작하게 한다. (O6·O8)
- [SHOULD] 권한(알림·위치)은 그 기능을 누른 순간에 이유 한 줄과 함께 요청한다. (O3·O4·O10)
  - 비회원 결제를 가장 눈에 띄게 두고, 계정 생성은 완료 화면에서 1~2필드로 받는다. 한국은 비회원 주문 조회 경로를 둔다.
  - 카카오·네이버 로그인은 이메일 폼 위에 둔다(§17). 효과는 가입이 아니라 가입 뒤 구매까지 잰다.

### 22-4. 유지·결제 실패
- [MUST] 결제가 실패하면 재시도 기간 동안 접근을 유지한다. 비차단 배너와 원클릭 카드 변경을 보이고, 복구되면 배너를 없앤다. (R1)
- [SHOULD] 스트릭은 매일 쓰는 것이 핵심 가치인 제품에만 쓰고, 유예권 2개와 7일 축하를 둔다. 해지 뒤 재가입 팝업을 되풀이하지 않는다. (R3·R4)
- [SHOULD] 소모품 구독의 관리 화면에는 배송 주기 변경과 한 번 건너뛰기를 해지 전 대안으로 둔다. (R5)
- [SHOULD] 앱 평점·리뷰 요청은 성공 순간 뒤에만 띄운다. 온보딩 중이나 페이월 앞에서는 요청하지 않는다. (V4 · Apple HIG)

### 22-5. 신뢰·리뷰
- [MUST] 신뢰 요소(구체적 보증·결제 보안·실명 후기·반품 조건)는 CTA·결제 버튼 옆에 둔다. 숫자 증거(고객 수·평점)는 현재 값이고 검증할 수 있을 때만 쓰며, 기준일과 리뷰 수를 함께 적는다. 가짜 인증 씰은 금지한다. (T1·T2·T4)
- [MUST] 평점 분포 막대는 누르면 그 별점으로 필터된다. 부정 리뷰를 숨기지 않고, 판매자 답변은 스타일로 구분한다. 리뷰가 5개 이하면 분포를 숨긴다. (T5)
- [SHOULD] 보증은 구매 CTA 바로 아래 한 줄로 쓴다(기간·범위, 조건 2개 이하, 청약철회 법정 기간과 충돌하지 않게). 결제 입력부는 색 패널·자물쇠·실제 PG 마크 1~2개로 감싼다. 인증 구매자 배지를 단다. 리뷰 0개 상품은 첫 리뷰 요청을 우선한다. 포토·영상 리뷰 갤러리를 텍스트 리뷰 위에 둔다. (T3·T4·T6·T7)
- [SHOULD] 리뷰 이벤트 보상은 작성한 뒤에 준다. 별점은 기본값 없이 받는다(미리 채운 5점 금지). (T9)
- [SHOULD] About·회사 소개는 AI가 읽을 수 있는 **브랜드 사실표**로 만든다: 한 줄 정의, 수치가 있는 차별점 3~5개, 경영자 실명, `<dl>` 핵심 사실(설립·위치·사업자 정보), 자주 묻는 질문. (X11)

### 22-6. 획득 표면
- [MUST] **히어로는 5초 안에 답한다:** 무엇인지, 누구를 위한 것인지, 누르면 무엇이 일어나는지. (A1~A3)
  - 뷰포트마다 주 CTA는 하나다. 첫 모바일 뷰포트 안에 두고, 증거 섹션 뒤에 반복한다.
  - CTA 문구는 동사+받는 것으로 쓴다(「확인·제출·더보기」 금지). 한국어는 해요체·능동형으로, 다음 화면이 예측되게 쓴다.
- [MUST] 팝업은 닫기·거절 링크·바깥 클릭·Esc로 닫히고, 포커스를 가두며, 닫힌 것을 기억한다. 첫 화면을 가리는 모달은 금지한다. 이탈 의도 팝업은 장바구니·결제에만, 방문당 1회만 띄운다. (A5·A6)
- [SHOULD] 짧은 전환 폼은 페이지 안에 둔다. 리드 캡처는 이메일 하나만 받고, 받을 것을 미리 보여 주고, 도착 시점을 적는다. (A4·A7·A8·A10·V1·V2)
  - 공지 띠는 한 메시지만 담고, 닫을 수 있게 하고, 기간이 끝나면 없앤다.
  - 완료 페이지에는 다음에 일어날 일, 도움 받을 곳, 다음 행동 하나를 보인다.
  - 추천은 성공 순간 직후 제품 안에서 요청한다. 양쪽 보상은 제품 가치로 주고, 문구를 채운 원클릭 공유와 진행 상태판을 둔다.
- [SHOULD] 상세페이지는 문제 → 공감 → 해결 → 설명 → 근거 순서로 쓴다. 후기는 위쪽으로 올리고, CTA 바로 아래에 배송·반품 한 줄을 둔다. 근거는 업체 사례 수치뿐이다. (A12)
- [MUST] 해외 CRO 조언 중 「해지 버튼을 덜 띄게」는 따르지 않는다(22-1 L3). 페이월을 떠날 때 윈백 제안은 한국에서 1회만, 거절할 수 있게, 「7일간 보지 않기」와 함께 띄운다.

### 22-7. AX — 에이전트와 AI 검색이 읽는 마케팅
- [MUST] CTA는 `<a href>`·`<button>`으로 만들고 동사형 접근 이름을 붙인다. 아이콘 버튼에는 aria-label을 단다. `div[onclick]`은 금지한다. (X1)
- [MUST] 가격·요금제명·CTA·사양·영업시간은 서버가 그린 첫 HTML의 텍스트로 둔다. 이미지 속 글자(상세페이지 통이미지 포함)에는 텍스트 대응물이 필수다. 핵심 정보를 모달·로그인·쿠키벽 뒤에 두지 않는다. 쿠키 배너는 화면을 가리지 않는 형태로 두고, robots 기본값은 검색 봇 허용이다. (X2·X3)
- [MUST] JSON-LD는 화면과 같은 props에서 생성하고, 그 값이 화면 텍스트에 있어야 한다. 별점 마크업은 Product에만 단다. 자체 후기(Organization·LocalBusiness)에는 달지 않는다. (X4)
- [SHOULD] (X5~X10)
  - 바뀌는 정보에는 갱신일을 보이고 dateModified를 단다. IndexNow는 옵션이다.
  - 근거 문장에는 수치·출처·날짜를 적고, 키워드를 반복하지 않는다.
  - Organization 마크업은 홈 1곳에만 둔다(taxID·sameAs).
  - AI 유입(`utm_source=chatgpt.com` 등)은 별도 채널로 잰다.
  - WebMCP 선언형 속성은 검색·문의·예약 폼에만 옵트인으로 단다. 결제에는 자동 제출을 금지한다.
  - FAQPage JSON-LD와 llms.txt는 기본 끔이다. 효과를 주장하지 않는다.

### 22-8. 계측
- [MUST] 퍼널 단계·폼 필드 이벤트는 `block-contract`의 `EVENTS` 규약으로 낸다. 이벤트 속성에 개인정보를 넣지 않고, 계측은 동의 상태를 따른다. (M1)
- [SHOULD] 세션 1,000개·전환 30건 미만의 차이는 잡음으로 본다. 외부 사례의 상승률을 우리 결과처럼 주장하지 않는다. (M2)

### 22-9. 확인 안 됨 (사람이 확인)
- 요금제 추천 배지가 「잘못된 계층구조」에 해당하는가
- 요금제 주기를 미리 선택해 두는 것이 사전선택 금지에 해당하는가
- 리뷰 적립금에 대가성 표시 의무가 있는가
- 네이버 AI 브리핑의 인용 기준

확인되면 이 절의 해당 줄을 고치고 날짜를 적는다.

## 23. 제품 화면 — 로그인 뒤 계정·결제·메일·오류·에이전트 경계

**규칙 ID.** U1~U21은 이 절의 규칙 번호이고 코드·시험의 인용이 가리킨다. §22가 「팔고 붙잡는 화면」이라면 이 절은 「가입한 사람이 쓰는 화면」이다. §7(상태)·§7-A(폼)·§7-B(오버레이)·§7-D(오류)·§12(AX)·§22를 제품 화면에 적용할 때의 바닥선을 적는다.

### 23-1. 어디인가 · 무엇이 됐나 · 다음은
- [MUST] **헤더는 서버가 처음 그릴 때부터 로그인 상태를 따른다.** 로그인한 사람에게는 계정 메뉴와 로그아웃을, 로그인 전에는 로그인·가입을 보인다. 로그인·가입·로그아웃·소셜 왕복 뒤 새로고침 없이 바뀐다. 로그아웃은 일반 내비와 떨어진 계정 메뉴 안에 둔다. 로그인한 채 로그인·가입·비밀번호 찾기 쪽을 열면 「이미 로그인했어요」와 계정으로 가는 길을 보인다. (U1)
- [MUST] **쪽을 건너는 흐름이 끝나 도착한 화면은 결과를 화면에 남는 글로 말한다.** 소셜 로그인·메일 링크·결제 복귀·로그아웃 뒤의 도착 화면에 `role="status"`(실패면 `role="alert"`) 글과 다음 행동 하나를 서버 HTML로 둔다. 사라지는 토스트만으로 두지 않는다. 주소의 표지(`?welcome=`·`?error=`)는 한 번 읽고 지운다. 실패 갈래(사용자 취소·공급자 오류·이미 있는 이메일·만료·재사용 링크)마다 도착 문구와 다시 시도할 길이 있다. 성공 글은 사실만 말한다(이동하지 않으면서 「이동 중」이라 쓰지 않는다). (U2)
- [MUST] **로그인이 필요한 화면에 로그아웃·만료 상태로 오면 로그인 안내와 돌아올 주소를 준다.** 읽기 오류·빈 화면·「다시 불러오기」로 보이지 않게 하고, 로그인 뒤 그 자리로 돌아온다(`returnTo`). [SHOULD] 세션이 끝나기 전에 경고하고 입력 중인 값을 보존한다. (U3 · §7-A 20초)

### 23-2. 가입 뒤 계정
- [MUST] **확인 메일 흐름**: 보낸 주소를 그대로 보이고 주소를 고칠 길, 스팸함 안내, 다시 보내기(대기 시간 표시)를 둔다. 메일에는 링크 유효 시간과 「내가 가입하지 않았어요」 경로를 둔다. 확인 전인 계정은 계정 화면에 표지를 달고, 로그인 뒤에도 다시 보낼 자리가 있다. 확인 링크를 로그아웃 상태로 열면 다음 행동은 로그인이다. (U4)
- [MUST] **비밀번호**는 길이를 우선한다(8자 이상, 흔하거나 유출된 비밀번호는 거절). 붙여넣기와 비밀번호 관리자를 허용하고, 규칙은 입력 전에 보인다. 오류가 나면 포커스는 그 칸으로 간다. (U5 · NIST SP 800-63B)
- [SHOULD] **2단계 인증**: `autocomplete="one-time-code"`·`inputmode="numeric"`·붙여넣기 허용. 켤 때 복구 코드를 보여 주고 저장했는지 확인한 뒤 켠다. 방법(인증 앱·보안키·패스키)을 고르게 한다. 비밀번호 재설정 완료 화면은 다른 기기 로그아웃 여부를 말한다. 2단계 스위치는 코드 입력 화면이 있을 때만 켤 수 있다. (U6)
- [MUST] **계정 설정은 다섯 구획**(프로필·보안·결제·알림·내 데이터)으로 두고 위험 행동(탈퇴)은 맨 아래 별도 구획에 둔다. 서버 기능이 있는 계정 행동(비밀번호·이메일 변경, 기기 목록, 수신 철회, 내려받기, 탈퇴)은 모두 이 화면에서 닿는다. **탈퇴 화면**은 지워지는 것·법정 보관으로 남는 것·유예 마감일·되돌리는 법을 말하고, 대상 이름 입력(§7-B)을 받고, 같은 화면에 내 데이터 내려받기를 둔다. 접수·완료는 메일로 알린다. (U7)
- [MUST] **화면 글은 존재하는 기능만 약속한다.** 「설정에서 끌 수 있어요」·「끝나기 전에 알려 드려요」·「문의해 주세요」·「나중에 추가할 수 있어요」 같은 글은 그 기능이 화면·메일·경로로 있을 때만 쓴다. 문구 파일과 기능은 정적 관문(`check:ux-static`)으로 묶는다. (U8)

### 23-3. 결제·구독
- [MUST] **요금표의 행동은 로그인 상태를 따른다.** 로그인한 사람의 「요금제 고르기」는 가입이 아니라 결제(`/upgrade?plan=`)로 가고, 고른 요금제가 실린다. 결제 화면은 헤더·요금표·결제 관리에서 닿는다. (U9)
- [MUST] **결제창을 닫고 돌아온 화면은 웹훅이 늦어도 「구독 없음」으로 보이지 않는다**: 확인 중 → 완료, 또는 「메일로 알려 드릴게요」. 결제 오버레이는 포커스를 가두고 닫으면 트리거로 돌려준다. [SHOULD] 지난 결제 내역·영수증 열람 길(또는 판매 대행자 포털)을 두고, 영수증이 어느 메일로 가는지 말한다. (U10)
- [MUST] **결제 실패**: 다음 재시도 날짜·접근 유지 마감일·카드 변경 한 번 클릭을 한 배너에 보인다. 배너는 접근을 막는 모달이 아니고 `role="alert"`로 알린다. 실패한 결제를 정상 일정(「다음 결제일」)처럼 보이지 않는다. 복구되면 배너를 없애고 확인 글을 보인다. 실패 메일의 링크는 카드 변경 화면으로 바로 간다. (U11 · §22-4 R1 구체화)
- [MUST] **체험 종료·갱신·가격 변경은 미리 알리고 사람이 답한다.** 체험 종료·연 갱신 전 예고 메일을 보낸다(시점은 §22-2 P6~P10). 가격 변경 동의·거절 링크의 도착 쪽은 존재하고(관문 N05), 동의·거절은 사람이 누른다. 해지·만료 뒤 결제 관리 화면에는 「다시 시작」이 한 번에 닿는다. 이미 해지 예약이면 해지 흐름 대신 상태와 「해지 취소」를 보인다. (U12 · §22-1 L6)

### 23-4. 메일·알림
- [MUST] **거래 메일 형식**: 제목에 제품 이름과 해야 할 일. 첫 줄에 행동 하나. 버튼 아래 글자 링크(버튼이 안 열릴 때). 링크 유효 시간. 왜 이 메일을 받는지. 화면과 같은 언어. 광고성 내용을 섞으면 광고 표기와 수신 거부를 따른다. 거래 메일과 마케팅 메일은 발송 도메인·스트림을 나누고 SPF·DKIM·DMARC를 맞춘다. (U13)
- [MUST] **마케팅 수신**: 동의 결과를 통지하고, 철회는 계정 화면과 메일의 원클릭 수신 거부(`List-Unsubscribe`·`List-Unsubscribe-Post`, RFC 8058)로 즉시 반영한다. 묻는 채널은 제품이 실제로 쓰는 것만. 알림은 종류·채널별로 끌 수 있고, 필수가 아닌 알림은 기본 끔에 빈도 상한을 둔다. 법 조항은 해당 법령의 현행 조문을 따른다. (U14 · 정보통신망법 §50)

### 23-5. 오류·로딩·언어
- [MUST] **앱 전체 오류·로딩 화면을 둔다**(Next 기준 `error.tsx`·`global-error.tsx`·`loading.tsx`, CSP를 지키는 것). 404·500에는 헤더·내비·지원 경로를 둔다. 오프라인이면 띠로 알리고, 작성 중인 입력을 보존한다. (U15 · §7-D)
- [MUST] **오류 문구 구조**: 무엇이 잘못됐나 · 사용자 잘못인지 아닌지 · 다음 행동 하나 · 다시 해도 소용없는 오류면 지원 경로와 요청 번호. 입력값은 지우지 않는다. 기계가 읽을 수 있게 오류 영역에 코드(`data-error-code`)를 같이 둔다. 로그인 뒤 모든 화면에서 도움·문의에 한 번에 닿는다. (U16)
- [MUST] **한 화면 한 로캘**: 문구·날짜·숫자·통화·`aria-label`·`title`·메일 제목이 화면 로캘 하나를 따른다. 날짜는 월 이름을 글자로 쓰고(숫자만의 `10/03`은 나라마다 다르게 읽힌다) `<time datetime>`에 기계 값을 둔다. 시각은 사용자 시간대로 보이고, 화면과 메일이 같은 날짜를 말한다. 렌더 결과를 관문(G9)으로 잰다. (U17)

### 23-6. 접근성·구조 바닥선
- [MUST] 제품 화면의 모든 쪽은 첫 Tab이 「본문으로 건너뛰기」이고 그 목적지 `main`이 있으며, 쪽마다 `h1`이 하나다(로고·제품 이름이 아닌 그 쪽의 제목). 대화상자를 닫으면 포커스가 트리거로 돌아온다. 누름 대상은 44px 이상이다. 동의 띠는 375px 화면의 1/5 이상을 가리지 않는다. 출시 전에 실제 스크린리더로 가입 → 결제 관리 → 탈퇴를 한 번 듣는다. (U18 · §10-A · §14-10)
- [MUST] **제품 앱 머리 기본값**: 제목 템플릿(「쪽 · 제품」), 메타 설명·OG, `robots`(로그인 쪽 noindex), `favicon`·`manifest`. 약관·개인정보·환불 쪽은 내용을 채운 판으로 출시하고(stamp 관문), 모든 쪽 푸터에서 닿으며 사업자 정보·문의를 둔다. 사업자 정보(상호·운영자 성명·주소·전화·이메일·등록번호·호스팅 업체)는 제품 설정에서 읽고 빈 칸은 숨긴다 — 공장 코드·블록·예시에는 실제 값을 넣지 않는다(공장은 다른 사람도 쓴다). 쿠키 동의는 푸터에서 다시 열어 바꾸거나 철회할 수 있다. (U19)

### 23-7. 에이전트 자율·승인 경계
- [MUST] **행동을 위험도로 나눈다.** 조회·검색·값 채우기·초안은 에이전트가 해도 된다. 결제·요금 변경·해지·탈퇴·이메일 변경·동의·개인정보 제공·메시지 발송은 사람이 요약을 보고 누른다. 사람 승인 행동은 (1) 별도 확인 단계나 화면, (2) 눈에 보이는 안내 글, (3) 기계가 읽는 표지(`data-requires-human`)를 함께 갖는다. 확인은 이 승인 행동에만 건다 — 모든 단계에 걸면 승인 피로로 확인이 무력해진다. WebMCP 선언(`toolname`)은 사람이 마지막에 누르는 검색·문의·예약 폼에만 단다. 서버는 승인 행동을 확인 입력(확인 토큰·명시 동의 칸)과 함께 받아 실행한다. (U20 · §20-6 · §22-7 X10)
- [MUST] **에이전트·자동화의 실패와 멈춤을 말한다**: 무엇을 하려 했고 어디까지 했나 · 왜 멈췄나 · 사람이 할 다음 행동 하나 · 사람에게 넘기는 길. 글과 기계 값(`ActionResult.code`·`retryable`)을 함께 둔다. 사람 승인을 기다려 멈춘 것은 실패가 아니라 「승인 대기」로 알린다. (U21 · GOV.UK problem-with-the-service · NN/g error-message-guidelines)

### 23-8. 관문 — 이 절을 재는 것
