## G-hosting — 호스팅 (Vercel)

- 왜: 사이트를 인터넷에 올려 **진짜 주소**를 얻는 장이다. 도메인·로그인·결제·메일 장이 모두 이 주소를 쓴다.
- 준비물: 사이트 코드가 든 폴더(또는 저장소), Vercel 에 가입할 이메일.
- 등록 1 — Vercel 계정을 만든다. 무료 플랜(Hobby)은 개인·비상업 용도로 정해져 있다. 결제·판매를 받는 사이트는 상업 용도라 유료 플랜이 맞다.
- 설정: Vercel 에 새 프로젝트를 만들고(새 프로젝트나 만들기처럼 보이는 버튼) 사이트 코드를 연결한다. 코드가 저장소의 하위 폴더에 있으면 프로젝트의 루트 폴더 설정을 그 폴더로 맞춘다. 함수 지역은 코드의 `vercel.json` 이 정한다(서울).
- 설정: 환경 변수 `LF_MODE` 를 `live` 로 넣는다. 운영 실행(Vercel 배포)에서 `mock` 이면 서버가 켜질 때 멈춘다. 비어 있어도 멈춘다.
- 설정: 환경 변수 `CRON_SECRET` 을 넣는다. 예측하기 어려운 긴 값(16자 이상)을 직접 만들어 대시보드나 `vercel env add CRON_SECRET` 표준 입력으로만 넣는다. 정기 실행(Cron)이 이 값을 Authorization 머리로 붙여 부르고, 값이 없으면 정기 실행 경로는 401 이다.
- 설정: 첫 배포를 한다. 새 프로젝트의 **첫 배포는 늘 Production 환경**이 된다(Preview 로 올리려 해도). 끝나면 배포 주소가 나온다 — 이것이 **진짜 주소**다.
- 설정: 환경 변수 `NEXT_PUBLIC_APP_URL` 에 그 주소(`https://` 로 시작, 경로 없이)를 넣고 **다시 배포**한다. 앱 주소는 쿠키·로그인 콜백·메일 링크의 기준이다. 환경 변수는 바꾼 뒤 **새로 만든 배포부터** 적용된다(이미 올라간 배포는 그대로).
- 환경 구분: Vercel 의 환경 변수는 Production·Preview·Development 로 따로 넣는다. 실제 손님이 쓰는 값은 Production 에 넣는다. Preview 주소에는 Vercel 로그인 보호가 걸려 있을 수 있어(프로젝트 설정에 따라 다르다) 외부 서비스의 웹훅이 막힌다 — 웹훅·결제 완료 알림은 Production 주소로 받는다.
- 다른 키(DB·로그인·메일·결제 등)는 각 기능의 장에서 같은 방식(대시보드 또는 표준 입력)으로 넣는다.
- 확인: 배포 상태가 정상(Ready)이다. 주소를 열면 사이트가 보이거나, 아직 다른 장의 이름이 없으면 오류 화면이다 — 오류 화면은 정상이다. 서버는 켜질 때 빠진 환경 변수 **이름**을 한 번에 로그에 남긴다(값은 남기지 않는다). 사이트 폴더에서 `npm run env:check -- --vercel production` 은 Production 에 있는 이름과 필수 이름을 견준다(값은 읽지 않는다). Vercel CLI 가 없거나 로그인·프로젝트 연결이 없으면 이 점검은 건너뛴다.
- 막힘 1 — 배포가 실패하고 Cron 이야기가 나온다: 무료 플랜(Hobby)의 Cron 은 하루에 한 번까지만 돌게 할 수 있다. 이 키트의 `vercel.json` 에는 한 시간·30분·10분마다 도는 Cron 이 있어 Hobby 에서는 배포가 거절된다. 유료 플랜으로 올리거나 Cron 을 하루 한 번 이하로 줄여야 하는데, 줄이면 그 기능(예약 안내·결제 상태 맞추기 등)이 늦어진다.
- 막힘 2 — 주소를 열면 오류 화면이다: 로그에서 빠진 이름을 읽고 그 이름을 넣은 뒤 다시 배포한다. 값은 로그에 나오지 않는다.
- 막힘 3 — 변수를 넣었는데 그대로다: 변수 변경은 새 배포부터 적용된다. 다시 배포한다.
- 막힘 4 — 주소가 Vercel 로그인 화면으로 간다: Preview 주소에 걸린 로그인 보호일 수 있다. 손님에게 보일 주소는 Production 주소다.
- 출처: Vercel 문서 — 환경 변수, 환경(Production·Preview·첫 배포), Cron 사용량과 플랜 한도, Hobby 플랜과 공정 사용 안내, `vercel env` 명령. 이 저장소의 `.env.example`, `template/vercel.json`, `scripts/env-check.mjs`.

## G-analytics — 방문자 통계 (PostHog)

- 왜: 방문자 수와 많이 본 쪽을 보려면 PostHog 프로젝트가 하나 있어야 하고, 사이트는 그 프로젝트의 공개 키와 수집 호스트를 알아야 한다.
- 준비물: 이메일로 만든 PostHog 계정(없으면 가입), 호스팅 환경 변수 화면(`G-hosting`).
- 등록 1 — PostHog 계정과 프로젝트 하나. **가입할 때 클라우드 지역(US 또는 EU)을 고른다.** 지역마다 따로 가입하는 별도 클라우드다(EU 는 별도 주소에서 가입). 만든 뒤 지역을 직접 바꾸는 화면은 문서에서 확인하지 못했다. 미국 클라우드에서 유럽 클라우드로 옮기려면 앱 안에서 지원 요청을 해야 하고, 일부 유료 요금제만 받는다. PostHog 는 GDPR 을 중요하게 보면 EU 클라우드(프랑크푸르트 서버)를 권한다. 한국 사이트라면 어느 지역이든 국외 이전이다 — 고지 표는 키트가 `POSTHOG_HOST` 의 지역으로 만든다.
- 등록 2 — 프로젝트 토큰(공개 프로젝트 키, `phc_` 로 시작)을 프로젝트 설정 화면에서 확인한다 → `POSTHOG_PROJECT_KEY`. 브라우저에 실리는 공개 값이다.
- 등록 3 — (선택, 계정 삭제 기능이 있는 사이트만) 프로젝트 설정의 개인 API 키 칸에서 키를 하나 만든다. 이름을 붙이고 `person:write` 범위를 준다. 만든 뒤 다시 볼 수 없으니 바로 호스팅 환경 변수에 넣는다 → `POSTHOG_PERSONAL_API_KEY`. 프로젝트 숫자 id 는 프로젝트 설정이나 주소창에서 읽는다 → `POSTHOG_PROJECT_ID`.
- 설정: `POSTHOG_HOST` — 수집 호스트. US `https://us.i.posthog.com`, EU `https://eu.i.posthog.com`. 앱 화면 호스트(`us.posthog.com`·`eu.posthog.com`)를 넣어도 키트가 수집 호스트로 맞춘다. 프록시처럼 지역을 못 정하는 주소나 `http://` 이면 켜질 때 멈춘다.
- 설정: `POSTHOG_PROJECT_KEY` 와 `POSTHOG_HOST` **둘 다** 있어야 분석이 켜진다. 하나라도 없으면 분석만 꺼진다 — 분석 스크립트·동의 띠·「쿠키 설정」 링크·서버 계측이 사라지고 사이트는 그대로 켜진다. 키에 공백이 섞이면 켜질 때 멈춘다.
- 설정: 세 이름을 헷갈리지 않는다.

| 이름 | 무엇 | 비밀 | 어디에 |
|---|---|---|---|
| `POSTHOG_PROJECT_KEY` | 프로젝트 토큰(공개 키) | 아니오(브라우저에 실린다) | 분석 켜기 |
| `POSTHOG_PERSONAL_API_KEY` | 개인 API 키(프로젝트 토큰과 다르다) | **예** | 탈퇴자 데이터 지움, 서버 전용 |
| `POSTHOG_PROJECT_ID` | 프로젝트 숫자 id | 아니오 | 탈퇴자 데이터 지움 |

- 설정: 값은 호스팅 대시보드나 `vercel env add <이름>`(표준 입력)으로 넣는다. 환경 변수를 바꾸면 이미 있는 배포에는 적용되지 않고 새 배포부터 적용된다.
- 동의: 방문자가 분석에 동의하기 전에는 아무것도 보내지 않는다. 브라우저에서는 동의 전에 분석 라이브러리를 불러오지도 않고, 서버 이벤트도 동의가 참일 때만 나간다. 동의 띠는 분석이 켜졌을 때만 그려진다. 이 동의는 분석 쿠키 동의이고, 마케팅 메일 수신 동의(`G-consent`)와 별개다.
- 탈퇴 지움: 계정 삭제 기능이 있고 분석이 켜져 있으면 파기 Cron 이 PostHog 의 사람·이벤트·녹화를 지운다. 이때 `POSTHOG_HOST` · `POSTHOG_PERSONAL_API_KEY` · `POSTHOG_PROJECT_ID` 가 모두 있어야 한다. 분석을 켰는데 뒤의 둘이 없으면 지움 단계가 실패로 남고 계속 다시 시도한다(DB 파기는 그대로 돈다). PostHog 쪽 삭제는 배경에서 처리된다.
- 확인: `npm run env:check -- --vercel` 경고 없음 → 새로 배포 → 사이트에 동의 띠가 나옴 → 허용 → PostHog 프로젝트의 이벤트 화면에 방문 기록이 보임. 허용 전에는 PostHog 로 가는 요청이 없는지 브라우저 개발자 도구의 네트워크 탭으로 본다.
- 막힘: 동의 띠가 안 나온다 → `POSTHOG_HOST` 나 `POSTHOG_PROJECT_KEY` 가 배포에 없다(분석이 꺼진 것). 환경 변수를 넣은 뒤 새로 배포했는지 본다.
- 막힘: 이벤트가 안 보인다 → 동의 전에는 0건이 정상이다. 동의했는데도 없으면 호스트의 지역이 프로젝트를 만든 지역과 같은지 본다(지역마다 별도 클라우드다).
- 막힘: 앱이 켜질 때 멈춘다 → `POSTHOG_HOST` 가 `https://` 가 아니거나 프록시 주소, 또는 `POSTHOG_PROJECT_KEY` 에 공백이 섞였다.
- 막힘: 탈퇴 파기 Cron 의 분석 지움이 실패로 남는다 → `POSTHOG_PERSONAL_API_KEY` 나 `POSTHOG_PROJECT_ID` 가 비었거나, 키가 개인 API 키가 아니라 프로젝트 토큰이다.
- 출처: PostHog 공식 문서 — 데이터 저장·개인정보 안내, GDPR 안내, 제품 분석 시작·가격 안내(무료 구간과 사용량 과금 구조), 라이브러리 설치 안내(프로젝트 토큰과 호스트), 마이그레이션 가이드의 개인 API 키·프로젝트 id 얻는 법(posthog.com). Vercel 환경 변수 문서(vercel.com). 이 저장소의 `.env.example`.

## G-biz-kr — 한국 사업 등록 (사업자등록 · 통신판매업 신고 · PG 가맹)

법률·세무 자문이 아니에요. 관할 기관(국세청·시군구)이나 전문가에게 확인하세요.

- 왜: 한국에서 사이트로 돈을 받으려면 순서가 있다. 사업자등록 → 통신판매업 신고 → 카드 결제(PG) 가맹 심사. 앞 단계가 끝나야 다음 단계 서류가 나온다.
- 준비물: 신분증, 사업 종류와 사업장 정보, 실제로 물건·서비스를 파는 사이트 주소(호스팅·도메인 장 뒤).
- 등록 1 — 사업자등록: 세무서를 찾아가거나 국세청 홈택스에서 신청한다. 사업을 시작한 날부터 20일 안에 신청한다. 처리에 며칠이 걸린다. 정확한 날수는 [확인 안 됨] — 세무서나 홈택스 안내에서 확인한다.
- 등록 2 — 통신판매업 신고: 사업자등록과 **별개의 신고**다. 사업장 관할 시군구에 정부24 또는 방문으로 신고한다. 처리에 며칠이 걸린다. 정확한 날수는 [확인 안 됨] — 정부24 안내나 관할 시군구에서 확인한다. 대금을 먼저 받는 방식이면 신고할 때 구매안전서비스 이용확인증을 내야 한다. 신고 대상이 아닌 경우(면제)가 있을 수 있으니 해당하는지는 관할 시군구에 확인한다.
- 등록 3 — PG 가맹: 이 키트에 어댑터가 있는 카드·간편결제 연동은 PortOne(V2) 하나다(성과 `shop`). PortOne 에서 전자결제를 신청하고 사업자 정보를 내면 PG 사가 평균 3영업일 안에 연락해 입점 가능 여부를 본다. 입점 가능 여부는 실제 상품이 팔리는 사이트가 세팅돼 있어야 확인된다. 계약 뒤 카드사 심사가 약 2주 걸리고, 심사가 끝나기 전에는 실제 결제가 실패한다. 승인 뒤 값을 호스팅에 넣는 일은 상점 결제 장(`G-payments-kr`)에서 한다. 해외 카드 구독(Paddle)은 `G-billing` 장이고 이 장의 PG 가맹과 다른 길이다.
- 설정: 등록이 끝나면 사이트에 사업자 정보를 넣는다. 환경 변수 `LF_BUSINESS_NAME`·`LF_BUSINESS_ADDRESS`·`LF_BUSINESS_PHONE`·`LF_BUSINESS_EMAIL` 을 호스팅 대시보드에 넣는다. 대표자·사업자등록번호·호스팅 제공자·통신판매업 신고번호 칸의 이름은 `.env.example` 의 「사업자 정보」 절에 있다. 신고번호는 신고가 끝난 뒤에만 넣는다. 푸터가 값이 있는 칸만 그린다.
- 확인: 사이트 푸터에 사업자 정보가 보인다. 사이트 폴더에서 `npm run doctor -- --stage preview` 를 돌리면 표시해야 할 칸이 비어 있을 때 경고한다(값은 출력하지 않는다).
- 막힘 1 — 순서가 거꾸로다: 통신판매업 신고와 PG 가맹은 사업자등록 서류가 있어야 한다. 사업자등록부터 한다.
- 막힘 2 — 신고 서류가 모자란다고 한다: 대금을 먼저 받는 방식이면 구매안전서비스 이용확인증이 빠졌는지 본다.
- 막힘 3 — PG 사가 입점이 어렵다고 한다: PG 사마다 받는 업종이 다르다. 사이트가 세팅돼 있어야 심사가 된다는 점도 본다.
- 막힘 4 — 계약했는데 실제 결제가 실패한다: 카드사 심사가 끝나기 전이다. 약 2주를 기다린다(고칠 수 없다).
- 출처: 국세청(사업자등록 안내·홈택스), 정부24(통신판매업 신고), 공정거래위원회(통신판매업 등록 정보), 한국소비자원 소비자24(구매안전서비스 안내), PortOne 개발자 문서·도움말(전자결제 신청, PG 계약, 카드사 심사). 이 저장소의 `.env.example`, `packages/payments-kr`.

## G-db — 데이터베이스 (Supabase Postgres)

- 왜 필요한가: 계정·구독·문의·예약 같은 기록을 저장할 Postgres 가 있어야 사이트가 실제로(`LF_MODE=live`) 켜진다. `LF_MODE=mock` 은 메모리 DB 라 가입이 필요 없다.
- 준비물: 이메일로 만들 수 있는 Supabase 계정. 호스팅(`G-hosting`)이 정해져 있어 환경 변수를 넣을 곳이 있어야 한다.
- 등록 1 — Supabase 가입.
- 등록 2 — 새 프로젝트 만들기(“새 프로젝트/만들기”처럼 보이는 버튼). 데이터베이스 비밀번호를 정해 비밀번호 관리자에 따로 보관한다. 지역은 서울(`Northeast Asia (Seoul)`)을 고른다 — 이 키트의 개인정보 방침 초안은 서울 DB 를 기준으로 한다. 다른 지역이면 방침의 DB 지역 값(`databaseRegion`)도 바꾼다.
- 등록 3 — 프로젝트 화면 위쪽의 “연결(Connect)”처럼 보이는 단추에서 연결 문자열 두 개를 복사한다. 앱용은 **트랜잭션 풀러(포트 6543)**, 마이그레이션용은 **직접 연결(포트 5432)**. 직접 연결은 IPv6 네트워크가 필요하고, IPv4 만 되는 PC 에서는 세션 풀러(포트 5432)를 쓴다. 문자열 안의 `[YOUR-PASSWORD]` 자리에 비밀번호를 넣는다 — `&` `#` `?` 공백 같은 예약 문자는 퍼센트 인코딩한다. 호스트·사용자 이름은 복사한 문자열 그대로 둔다(풀러 호스트는 지역으로 직접 만들 수 없고, 풀러의 사용자 이름은 직접 연결과 다르다).
- 설정 1: 앱용(6543) 연결 문자열을 호스팅의 환경 변수 `DATABASE_URL` 에 넣는다 — 호스팅 대시보드 또는 `vercel env add DATABASE_URL`(표준 입력). 형식은 `postgres://` 또는 `postgresql://` 로 시작해야 한다. 포트 6543 이면 키트가 prepared statement 를 자동으로 끈다(트랜잭션 풀러는 prepared statement 를 지원하지 않는다).
- 설정 2: 마이그레이션은 직접 연결(5432) 문자열로 한 번 돌린다. 배달된 사이트 폴더에서 이 PC 의 터미널 환경 변수로만 잠깐 넣는다.

  ```
  DATABASE_URL=<직접 연결 문자열> node db/migrate.mjs
  ```

  이미 적용한 파일은 건너뛴다. 포트 6543 이면 스크립트가 멈추고 직접 연결(5432)을 쓰라고 알린다. 새 버전을 받아 `db/migrations` 가 늘면 같은 명령을 다시 돌린다.
- 확인: 마이그레이션 끝에 `migrations applied` 한 줄이 나온다. 그 뒤 배포를 다시 하면 부팅이 `DATABASE_URL` 을 검사하고, 빠졌거나 형식이 틀리면 빠진 이름을 알리며 멈춘다(값은 알리지 않는다).
- 막힘:
  - `Use the direct connection (port 5432)…` 로 마이그레이션이 멈춤 → 6543 문자열을 넣었다. 직접 연결이나 세션 풀러(5432) 문자열로 바꾼다.
  - 연결이 거절되거나 비밀번호 오류 → 비밀번호의 예약 문자를 퍼센트 인코딩했는지, 복사한 사용자 이름·호스트를 그대로 썼는지 본다.
  - 직접 연결 문자열이 이 PC 에서 닿지 않음 → IPv4 만 되는 네트워크일 수 있다. 세션 풀러(5432) 문자열을 쓴다.
  - 무료 프로젝트가 멈춤 → Supabase 무료 프로젝트는 7일 동안 활동이 적으면 일시정지될 수 있다(정지 약 1주 전에 경고 메일이 온다). 정지 중에는 요청을 처리하지 못한다. 대시보드에서 프로젝트를 다시 켠다. 정지 뒤 복원할 수 있는 기간은 [확인 안 됨](Supabase 문서 안에서도 서로 다르게 적혀 있다). 정지를 막으려면 유료 요금제로 올리는 방법이 문서에 있다.
- 출처: Supabase 문서 — Connecting to Postgres(연결 방식·포트·prepared statement), Regions(서울 지역), About billing on Supabase(무료 프로젝트 개수), Project pausing(무료 프로젝트 일시정지). 이 저장소의 `packages/db`·`template/db/migrate.mjs`·`.env.example`.

## G-domain — 도메인 연결

- 왜: 호스팅이 준 주소 대신 **내 이름의 주소**를 쓰기 위해서다. 연결은 도메인을 사는 일, 주소록(DNS)을 호스팅에 맞추는 일, 앱이 아는 주소를 바꾸는 일의 세 가지다.
- 준비물: 호스팅 장에서 올린 프로젝트, 도메인 비용을 낼 결제 수단.
- 등록 1 — 도메인을 파는 곳(등록기관)에서 원하는 이름이 비어 있는지 찾아 산다. 도메인은 기간이 정해져 있고 기간이 끝나기 전에 갱신해야 한다. 갱신 방법과 기간은 파는 곳의 안내를 따른다.
- 설정: 호스팅(Vercel) 프로젝트의 도메인 화면에서 산 도메인을 추가한다. 루트 도메인(예: 이름 바로 뒤에 `.com`)과 하위 도메인(예: `www` 를 붙인 것)을 둘 다 쓸지 정한다.
- 설정: 주소록(DNS)을 호스팅에 맞춘다. 두 방법 중 하나를 고른다. (가) 도메인을 산 곳의 DNS 화면에서 레코드를 추가한다 — 루트 도메인은 A 레코드, 하위 도메인은 CNAME 레코드. 넣을 값은 Vercel 이 프로젝트의 도메인 화면에서 알려 주는 값을 그대로 쓴다. (나) 도메인의 네임서버를 Vercel 이 알려 주는 것으로 바꾼다 — 그러면 DNS 를 Vercel 에서 관리한다. 바꾸기 전에 지금 있는 레코드(메일용 MX, 인증용 TXT 등)를 Vercel 쪽에 먼저 똑같이 옮겨 둔다. 안 옮기면 메일이 끊길 수 있다(Vercel 안내).
- 설정: 환경 변수 `NEXT_PUBLIC_APP_URL` 을 새 주소(`https://` 로 시작, 경로 없이)로 바꾸고 **다시 배포**한다. 환경 변수는 바꾼 뒤 새로 만든 배포부터 적용된다.
- 설정: 옛 주소를 적어 둔 다른 서비스를 새 주소로 고친다 — 로그인 공급자에 등록한 콜백 주소, 결제·메일 서비스의 웹훅 주소처럼 주소를 직접 적어 둔 곳. 해당 장에서 같은 이름의 항목을 찾아 고친다.
- 확인: Vercel 도메인 화면이 연결 정상을 보인다. 새 주소를 열면 사이트가 보이고 주소창에 보안 표시(HTTPS)가 있다. 인증서는 Vercel 이 자동으로 발급한다.
- 막힘 1 — 바꿨는데 안 열린다: DNS 변경은 퍼지는 데 시간이 걸린다. 네임서버 변경은 하루에서 이틀까지 걸릴 수 있다. 기다리는 수밖에 없다(고칠 수 없다). 그 사이 Vercel 화면은 아직 연결 안 됨으로 보일 수 있다.
- 막힘 2 — 연결은 됐는데 보안 경고가 뜬다: 인증서는 DNS 가 맞게 퍼진 뒤에 발급된다. 조금 기다린다. 도메인에 CAA 레코드가 있으면 인증서 발급 기관(Let's Encrypt)을 허용하도록 고쳐야 한다.
- 막힘 3 — Vercel 이 값이 틀렸다고 한다: 레코드 종류(루트는 A, 하위는 CNAME)와 값을 Vercel 이 알려 주는 것과 글자 단위로 견준다.
- 막힘 4 — 어느 날 사이트 주소가 멈췄다: 도메인 갱신 기간이 지났는지 파는 곳에서 본다.
- 출처: Vercel 문서 — 프로젝트에 도메인 추가·DNS 설정(A·CNAME·네임서버), 도메인 문제 해결(전파 시간), 자동 SSL 인증서(CAA 레코드 포함). 이 저장소의 `.env.example`.

## G-auth — 로그인·가입 (Better Auth)

- 왜 필요한가: 로그인 세션과 확인 메일 링크를 서명하는 비밀 하나와, 콜백·메일 링크가 돌아올 앱 주소가 있어야 `LF_MODE=live` 에서 가입·로그인이 켜진다.
- 준비물: `G-db` 가 끝난 프로젝트(마이그레이션 적용). 배포 주소(호스팅이 주는 주소 또는 연결한 도메인). 소셜 로그인을 쓸 때만 해당 공급자 계정.
- 등록 1 — (선택, Google 로그인) Google Cloud 콘솔에서 프로젝트를 만들고 사용자 인증 정보에서 OAuth 클라이언트 ID 를 “웹 애플리케이션” 종류로 만든다. 승인된 리디렉션 URI 에 `https://<도메인>/api/auth/callback/google`(로컬 시험은 `http://localhost:3000/api/auth/callback/google`)을 넣는다. 나온 클라이언트 ID·시크릿을 `GOOGLE_CLIENT_ID`·`GOOGLE_CLIENT_SECRET` 에 넣는다. 리디렉션 URI 가 앱 주소와 다르면 `redirect_uri_mismatch` 가 난다.
- 등록 2 — (선택, 카카오 로그인) 카카오디벨로퍼스에서 앱을 만든다. [카카오 로그인] 사용 설정을 ON 으로 한다(OFF 면 `KOE004`). 리다이렉트 URI 에 `https://<도메인>/api/auth/callback/kakao` 를 등록한다(틀리면 `KOE006`). [동의항목]을 설정한다. 앱의 REST API 키를 `KAKAO_CLIENT_ID` 에, 그 키의 클라이언트 시크릿을 `KAKAO_CLIENT_SECRET` 에 넣는다. 이메일(`account_email`)을 받으려면 비즈 앱이어야 한다(Better Auth 문서). 일부 개인정보 동의항목은 비즈 앱 전환 → 신청 자격 확인 → 비즈니스 정보 심사 뒤 추가 기능을 신청해야 하고 그 심사에는 며칠이 걸린다(정확한 날수는 [확인 안 됨] — 카카오 안내에서 확인한다). 비즈 앱 전까지는 이메일이 없으므로 이 키트가 카카오 회원번호로 만든 대체 주소를 계정 이메일로 쓴다.
- 등록 3 — (선택, 네이버 로그인) 네이버 개발자 센터에서 애플리케이션을 등록한다(처음 한 번 휴대폰 인증). 사용 API 에 “네이버 로그인”을 넣고 서비스 환경(PC 웹·모바일 웹)에 서비스 URL 과 네이버 로그인 Callback URL `https://<도메인>/api/auth/callback/naver` 를 넣는다(Callback URL 은 최대 5개). 나온 클라이언트 아이디·시크릿을 `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET` 에 넣는다. 실서비스로 열려면 검수를 요청해 승인받아야 하고, 승인 전에는 로그인할 수 있는 아이디가 제한된다.
- 설정 1: 비밀 `BETTER_AUTH_SECRET` 을 만든다. 32자 이상이어야 하고 엔트로피가 높아야 한다(Better Auth 문서). 만드는 표준 방법은 `openssl rand -base64 32`. 만든 값은 화면에 붙여 넣지 말고 호스팅 대시보드 또는 `vercel env add BETTER_AUTH_SECRET`(표준 입력)에 바로 넣는다. 32자 미만이면 live 에서 부팅이 멈춘다. 서명 비밀을 바꾸지 않는다. 확인 메일의 “제가 가입한 게 아니에요” 링크의 서명 비밀이 `BETTER_AUTH_SECRET` 에서 만들어지므로, 바꾸면 이미 나간 그 링크가 더는 맞지 않는다.
- 설정 2: 앱 주소 `NEXT_PUBLIC_APP_URL` 을 `https://` 로 시작하는 배포 주소로 넣는다. live 에서는 필수다 — 이 키트는 이 값을 인증의 기준 주소로 쓰며, 소셜 로그인 콜백과 메일 링크가 이 주소로 만들어진다. 배포 주소는 첫 배포 뒤에야 알 수 있으니 순서는 배포 → 주소 확인 → 값 추가 → 다시 배포. 도메인을 연결하면(`G-domain`) 그 주소로 바꾸고 다시 배포한다.
- 설정 3: 소셜 공급자는 `<공급자>_CLIENT_ID` 와 `<공급자>_CLIENT_SECRET` 을 **둘 다** 넣은 것만 켜진다. 하나만 있으면 켜지지 않는다(점검 도구가 경고한다). 하나도 없으면 이메일·비밀번호 로그인만 있다.
- 설정 4: 비밀 `SUBJECT_REF_KEY` 를 만든다. 32자 이상이어야 하며 live 에서는 필수다. 탈퇴한 사람의 거래 기록을 이메일 없이 가리키는 데 쓰는 키라서, 바꾸거나 잃어버리면 옛 기록을 찾지 못한다. 값은 화면에 붙여 넣지 말고 호스팅 대시보드 또는 `vercel env add SUBJECT_REF_KEY`(표준 입력)에 바로 넣고, 한 번 정하면 바꾸지 않는다.
- 확인: 배포 주소에서 가입 화면이 열린다 → 이메일로 가입하면 확인 메일이 온다. 소셜을 켰다면 로그인 화면에 그 공급자 버튼이 보이고 눌러서 공급자 화면을 거쳐 돌아온다. 소셜로 처음 오면 약관·개인정보·만 14세 확인을 거쳐야 계정이 생긴다(가입 없이 소셜로 로그인하면 `/sign-in?error=signup_disabled` 로 돌아와 안내를 본다).
- 막힘:
  - 부팅이 멈추고 `BETTER_AUTH_SECRET` 또는 `NEXT_PUBLIC_APP_URL` 을 알림 → live 에서 필수다. 이름이 호스팅 환경에 있는지, 값이 32자 이상인지 본다. 환경 변수를 바꾼 뒤에는 다시 배포한다.
  - 소셜 로그인에서 `redirect_uri_mismatch`(Google) / `KOE006`(카카오) → 공급자 콘솔에 등록한 콜백 주소가 `NEXT_PUBLIC_APP_URL` 의 주소와 글자까지 같은지 본다. 주소가 `localhost` 로 만들어지면 앱 주소 환경 변수가 빠진 것이다.
  - 카카오 `KOE004` → [카카오 로그인] 사용 설정이 OFF 이다. ON 으로 바꾼다.
  - 소셜 버튼이 안 보임 → 그 공급자의 ID·시크릿 둘 중 하나가 비어 있다.
- 출처: Better Auth 문서 — Installation(비밀·기준 주소), Google · Kakao 공급자 안내(콜백 주소·비즈 앱), Concepts/CLI(`secret` 명령). 카카오디벨로퍼스 — 카카오 로그인 설정하기(사용 설정·리다이렉트 URI·동의항목·심사). 네이버 개발자 센터 — 오픈 API 사전 준비 사항, 네이버 로그인 개발가이드(검수). Google Identity 문서. 이 저장소의 `.env.example`·`packages/auth`·`registry/feature-auth-betterauth`.

## G-admin — 관리 화면

- 왜 필요한가: 방문자가 남긴 것을 사장님이 한곳에서 보고 처리하려고 한다. 주문 발송, 예약 확정·취소, 문의 답변 상태, 후기 승인·숨김, 뉴스레터 명단, 가입자 정지를 이 화면이 한다. 화면은 설치되지만, 들어오는 사람을 정하는 일(소유자 메일 또는 관리자)은 운영자가 해야 켜진다.
- 준비물: 로그인(`G-auth`)과 데이터베이스(`G-db`)가 끝나 있어야 한다. 소유자 메일 경로를 쓰려면 문의 알림 메일 `INQUIRY_OWNER_EMAIL` 이나 예약 알림 메일 `BOOKING_OWNER_EMAIL` 중 쓰는 쪽이 정해져 있어야 하고, 그 주소로 가입해 메일 확인까지 마친 계정이 있어야 한다. 관리자 경로를 쓰려면 데이터베이스에 직접 한 줄을 고칠 수 있는 길(데이터베이스 서비스가 주는 질의 도구)이 있어야 한다.
- 등록: 없음. 외부 서비스 계정은 새로 필요 없다.
- 설정: 구획 일곱 개가 있고 부품이 꺼지면 그 구획도 사라진다 — 주문(`orders`)·재고(`stock`)는 판매(`commerce`), 예약(`bookings`), 문의(`inquiries`), 후기(`reviews`), 뉴스레터(`newsletter`), 사용자(`users`). 사이드바에는 들어온 사람이 볼 수 있는 구획만 보인다.
- 설정: 들어올 수 있는 사람은 두 종류다. **소유자** — 로그인했고 메일 확인을 마친 주소가 그 구획의 소유자 메일과 같은 사람(앞뒤 공백·대소문자는 무시, 둘 다 비어 있으면 안 된다). 문의·후기는 `INQUIRY_OWNER_EMAIL`, 예약은 `BOOKING_OWNER_EMAIL` 이다. 소유자는 2단계 인증 없이 들어온다. **관리자** — 사용자 행의 역할이 `admin` 이고 2단계 인증을 켠 사람. 역할은 쉼표 목록(`admin,support`)이어도 `admin` 이 들어 있으면 관리자다. 주문·재고·뉴스레터·사용자 구획은 관리자만 연다.
- 설정: 로그아웃한 사람, 관리자가 대신 들어온 세션(대리 로그인), 정지된 사람은 어떤 구획도 못 연다. 관리자 역할이어도 2단계 인증이 없으면 `two_factor_required` 로 막힌다(같은 사람이 그 구획의 소유자 메일이면 소유자로는 들어온다).
- 설정: 첫 관리자는 화면으로 만들지 않는다. 데이터베이스의 사용자 행에서 `role` 을 `admin` 으로 바꾼다. 그리고 `template/lib/launch/features.ts` 의 `AUTH_FEATURES` 를 `{ twoFactor: true, admin: true }` 로 바꾼다 — 기본값은 둘 다 꺼짐이고, 꺼져 있으면 관리자 입구는 열리지 않으며 사용자 구획도 사라진다.
- 설정: **지금 템플릿의 한계** — 계정 화면의 「2단계 인증」 줄은 일부러 숨겨져 있어, 화면에서 2단계 인증을 켜는 길이 없다. 그래서 관리자 전용 구획(주문 · 재고 · 뉴스레터 · 사용자)을 화면으로만 열 수는 아직 없다. 소유자 경로(문의 · 예약 · 후기)는 이 한계와 무관하게 열린다. 2단계 인증 등록 화면은 후속 일이다.
- 설정: 행동(상태 바꾸기·취소·숨김·정지)은 서버가 사람 확인 입력(`confirmed: true`)을 받지 않으면 실행하지 않는다. 되돌리기 어려운 행동은 구획당 하나가 위험 행동으로 따로 표시된다 — 주문 취소(환불), 예약 취소, 문의 불만 표시, 후기 숨김, 뉴스레터 수신 거부 처리, 사용자 정지. 관리자 전용 행동은 소유자에게 안 보이고 `forbidden` 이다.
- 설정: 연락처 열(메일·전화·이름)은 목록과 요약에서 일부만 보이게 가려 나간다(예: `k***@example.com`). 주문 상세의 받는 분·전화·주소는 배송에 써야 해서 가리지 않는다 — 읽을 때마다 접속 기록이 남는다.
- 설정: 읽기마다 접속 기록(`access_logs`) 한 줄, 행동마다 행동 기록(`admin_actions`) 한 줄이 남는다. 행동 기록에는 폼에 적은 값을 남기지 않는다. 읽기 기록이 실패하면 읽기도 거부한다. 요청 제한은 읽기 분당 120번, 쓰기 분당 30번이고 행동 입구에서 분당 60번이 한 번 더 걸린다.
- 설정: 화면(`/admin`, `/admin/<구획>`, `/admin/<구획>/<기록 id>`)은 검색엔진에 올리지 않는다(`noindex`). 구획이 던진 오류는 화면에 일반 문구로만 나가고, 서버 로그에는 오류 이름과 위치만 남는다.
- 설정: 설치 뒤 `next.config.ts` 의 `transpilePackages` 에 쓰는 `@launch-factory/*` 를 모두 적고, `serverExternalPackages` 에 `@electric-sql/pglite` 를 더한다(이 항목의 설치 안내 7번). 구획을 더하는 법은 `docs/guides/admin-sections.md` 에 있다.
- 설정: 예약 취소 환불 — 예약금이 있는 예약을 대표(소유자)나 시스템이 취소하면 때와 상관없이 기본으로 전액을 돌려준다. 비율은 `lib/launch/booking-config.ts` 의 `depositPolicy.ownerCancelRefundPercent`(0~100)로 바꾼다. 손님이 직접 취소할 때의 규정(취소 마감까지 전액, 그 뒤는 `laterRefundPercent`)은 그대로다.
- 설정: 알려진 한계 — 같은 사람이 `adminAct`(분당 60번)와 콘솔 쓰기(분당 30번) 두 한도를 함께 지난다. 검색 칸은 서버가 맞춘다 — 사용자·뉴스레터는 이메일, 문의는 접수 번호·이름·연락처, 예약은 접수 번호·이름·연락처(메일·전화), 후기는 제목·본문·작성자 이름이다. 후기에는 작성자의 이메일을 남기지 않아 이메일로는 찾을 수 없다(브라우저 시험으로 확인했다).
- 확인: 소유자 경로 — 소유자 메일로 가입·메일 확인 → 로그인 → `/admin` 에 문의·예약·후기 구획이 보임 → 시험 기록 하나를 열어 상세가 보임 → 행동 하나를 확인 입력과 함께 실행 → 상태가 바뀜. 관리자 경로 — 위 두 가지(역할 · `AUTH_FEATURES`)를 바꾸고 2단계 인증을 켠 계정이 있을 때 사용자·주문 구획이 보임. 막히는 쪽 확인 — 로그아웃 상태로 `/admin` 을 열면 로그인 안내만 보인다.
- 막힘: `/admin` 에 「들어갈 수 없음」만 보임 → 로그아웃, 대리 로그인, 정지, 소유자 메일 불일치(메일 확인을 안 마친 주소 포함), 또는 관리자 역할인데 2단계 인증이 없는 경우다. 어느 쪽인지는 화면이 숨기고 같은 문구로 답한다. 계정의 메일 확인 여부와 `role` 값을 먼저 본다.
- 막힘: 「볼 구획 없음」 → 들어오긴 했지만 그 사람이 열 수 있는 구획이 없다. 소유자 메일이 맞는 구획이 없거나, 관리자 전용 구획만 켜져 있는데 관리자가 아니다.
- 막힘: 사용자 구획이 안 보임 → `AUTH_FEATURES` 둘 중 하나가 꺼져 있다.
- 막힘: 행동이 `confirmation_required` 로 멈춤 → 오류가 아니라 사람 확인 대기다. 확인 단계를 지나야 실행된다.
- 막힘: 행동이 `invalid_state` 로 막힘 → 이미 그 상태다(예: 이미 취소됨). 두 번 눌러도 한 번만 실행되게 막아 둔 것이다.
- 막힘: 주문 취소를 눌렀는데 성공이라고 안 나옴 → 환불 도중 상태가 바뀌었다는 알림이다. 주문 상태를 다시 열어 확인한다.
- 출처: 저장소만 읽었다 — `registry/feature-admin-console` 의 설치 안내, `docs/guides/admin-sections.md`, `packages/admin-console` 의 입장 판단(`admit.ts`), 템플릿의 `lib/launch/admin-console.ts`·`admin-identity.ts`·`features.ts`와 구획 모듈 `lib/launch/admin-sections/`, 계획 3d 기록(PR 본문의 「남은 일」). 외부 서비스의 화면·주소는 없다.

## G-email — 메일 보내기 (Resend)

- 왜 필요한가: 사이트가 보내는 메일(가입 확인, 결제·가격 변경 안내, 문의·예약 알림 등)이 진짜로 나가려면 Resend 키와 DNS 로 인증한 발신 도메인이 필요하다.
- 준비물: 사이트 도메인과 그 도메인의 DNS 를 고칠 수 있는 곳(도메인 장 `G-domain`), 이메일 주소(Resend 가입).
- 등록 1 — Resend 계정을 만든다.
- 등록 2 — Resend 에 발신 도메인을 더한다. 사이트 도메인 그대로나 그 하위 도메인 중 하나를 고른다. Resend 가 DNS 레코드 목록(서비스가 보여 주는 레코드)을 낸다.
- 등록 3 — 그 레코드를 DNS 제공자에 그대로 추가한다. 보통 DKIM 서명용 레코드, 반송 처리용 `MX` 레코드, SPF 용 `TXT` 레코드가 나온다(발송 전용 하위 도메인에 붙는다). 값은 계정마다 다르니 Resend 화면에서 복사한다. 이어서 Resend 에서 DNS 확인을 누른다.
  - 기다림: 레코드를 바르게 넣으면 인증까지 시간이 걸리고 최대 72시간까지 걸릴 수 있다. 72시간 안에 레코드를 찾지 못하면 상태가 실패가 된다.
  - 권장: DMARC 는 자동으로 만들어지지 않는다. Resend 는 강하게 권장하므로 따로 추가한다(스팸함 방지).
- 등록 4 — Resend 에서 API 키를 만든다. 키는 만들 때 한 번만 보인다 → `RESEND_API_KEY`. 권한은 발송 전용(sending access)으로 줄 수 있고 특정 도메인으로 제한할 수도 있다. 발송 전용 키는 도메인 인증 상태를 읽지 못하므로 점검 도구(`scripts/doctor.mjs`)가 인증 확인 대신 경고를 낸다(고장은 아니다).
- 설정: 호스팅 환경 변수(대시보드 또는 `vercel env add <이름>` 표준 입력)에 `RESEND_API_KEY`, `EMAIL_FROM` 을 넣는다. `EMAIL_FROM` 은 `이름 <주소@인증한도메인>` 모양이고 **Resend 에서 인증한 도메인**이어야 한다. live 에서는 둘 다 필수다(없으면 켜질 때 멈춘다).
- 설정: 메일 안의 링크 기준 주소 `NEXT_PUBLIC_APP_URL`(배포 주소, live 필수)도 넣는다.
- 설정: 광고성 메일(`marketingAnnouncement` 템플릿)은 사업자 정보 `LF_BUSINESS_NAME`·`LF_BUSINESS_EMAIL`·`LF_BUSINESS_PHONE`·`LF_BUSINESS_ADDRESS` 가 모두 있어야 보낸다(하나라도 비면 던진다). 거래 메일은 영향이 없다. 광고성 메일을 한국 시각 밤 시간대에 보내지 않고 미루는 점검은 `LF_MARKETING_NIGHT_GUARD`(기본 켜짐, off 로 끈다).
- 설정: 제품 이름·기본 언어는 `lib/launch/config.ts` 의 `PRODUCT_NAME`·`DEFAULT_LOCALE` 을 제품에 맞게 고친다.
- 확인: 배포 환경에서 가입 확인 메일처럼 메일이 나가는 동작을 한 번 한다 → 받은편지함에 도착 → Resend 의 발송 기록(로그)에서 전달 상태를 본다. 점검 도구 `node scripts/doctor.mjs --stage preview` 의 `resend` 항목도 참고한다.
- 막힘: 인증이 오래 `pending` → 레코드 이름·값이 DNS 제공자에 정확히 들어갔는지, 같은 이름의 `MX` 가 충돌하지 않는지 본다(반송용 `MX` 는 발송 하위 도메인에 붙는다). 403 오류 → 인증 전에 `resend.dev` 테스트 주소로 보내면 계정 본인 주소로만 보낼 수 있다, 또는 `EMAIL_FROM` 이 인증한 도메인과 다르다. 메일이 스팸함으로 감 → SPF·DKIM·DMARC 셋이 모두 있는지 먼저 본다. 메일이 `suppressed` → 이전에 반송되거나 스팸 신고된 주소는 Resend 의 차단 목록에 올라 다시 보내지지 않는다. 광고성 헤더(`List-Unsubscribe`)가 DKIM 서명 대상에 들어가는지는 [확인 안 됨].
- 출처: Resend 문서(resend.com/docs) — 도메인 관리·인증 상태, 도메인이 인증되지 않을 때, API 키 만들기, 403 오류(resend.dev 도메인·도메인 불일치), 스팸 문제, 차단 목록. 저장소: `.env.example`, `registry/feature-email-resend` 의 설치 안내, `scripts/doctor.mjs`.

## G-billing — 카드 결제 · 정기구독 (Paddle)

- 왜 필요한가: 사이트가 요금제를 팔고 구독 상태를 받으려면 Paddle 계정, 가격, API 키, 알림(웹훅) 비밀이 있어야 한다. 이 중 어느 하나라도 없으면 결제가 열리지 않는다.
- 준비물: 이메일(계정 가입·확인), 사이트가 올라간 호스팅(알림 주소), 메일 장(`G-email`)과 데이터베이스 장(`G-db`)을 먼저 끝낸 상태. 실결제 전에는 사업자·본인 정보와 약관·개인정보처리방침·환불 정책 쪽이 공개된 사이트.
- 등록 1 — Paddle **샌드박스** 계정을 만들고 이메일을 확인한다. 샌드박스와 실결제 계정은 서로 다른 계정이고 API 키·클라이언트 토큰·알림 대상·상품·가격·고객이 서로 공유되지 않는다. 실결제 계정이 있어도 샌드박스 계정은 따로 만든다. 샌드박스는 인증 없이 바로 시험 결제를 받는다.
- 등록 2 — 샌드박스 대시보드에서 상품과 가격을 만든다(상품 하나에 가격을 붙인다. 정기구독이면 가격에 결제 주기를 두고, 체험이 있는 요금제는 체험 기간이 있는 가격을 따로 만든다). 만든 가격 id(`pri_` 로 시작)를 설정에 적는다.
- 등록 3 — 샌드박스에서 API 키를 만든다. 대시보드의 개발자 도구 쪽 인증 메뉴에서 새 API 키를 만들고, 필요한 권한만 고르고, 만료일을 정한다. 키는 만들 때 한 번만 보인다 → `PADDLE_API_KEY`. 키는 만든 뒤 기본 90일이 지나면 만료되고(Paddle 문서: 최대 1년까지 정할 수 있다) 만료되면 결제 호출이 실패하니, 만료 전에 새 키를 만들어 호스팅 환경 변수를 바꾸고 다시 배포한다.
- 등록 4 — 샌드박스에서 알림 대상(notification destination)을 만든다. 유형은 URL, 주소는 `https://<도메인>/api/webhooks/paddle`(저장소가 실제로 받는 경로). 받을 이벤트는 구독 이벤트(`subscription.*`)와 거래 이벤트(`transaction.completed`·`transaction.payment_failed`·`transaction.past_due`)다. 만든 뒤 그 알림 대상의 비밀 키를 복사한다 → `PADDLE_WEBHOOK_SECRET`. 알림 대상을 다시 만들면 비밀 키가 새로 나오니 호스팅 값도 바꾼다.
- 등록 5 — 샌드박스에서 기본 결제 링크(default payment link)를 정한다. 샌드박스는 도메인 승인이 필요 없다. Paddle 문서는 거래를 만들기 전에 기본 결제 링크를 정하라고 하고, 이 저장소의 어댑터도 이 링크를 요구한다.
- 등록 6 — 오버레이 결제를 쓰면 클라이언트 토큰을 만든다(같은 인증 메뉴). 샌드박스 토큰은 `test_` 로, 실결제 토큰은 `live_` 로 시작한다 → `PADDLE_CLIENT_TOKEN`(공개 값, API 키와 다르다). 비워 두면 결제는 Paddle 결제 링크로 이동한다.
- 등록 7 — 실결제 전환(서비스를 열 때만): ① 실결제 계정을 따로 만든다. ② 상품·가격·API 키·클라이언트 토큰·알림 대상을 실결제 쪽에 **다시** 만든다(샌드박스 것은 옮겨지지 않는다). ③ 웹사이트(도메인) 승인을 신청한다 — 실결제 결제창은 승인된 도메인에서만 열린다. ④ 도메인 승인 뒤 실결제 기본 결제 링크를 정한다(호스트가 승인된 도메인과 정확히 같거나 그 `www.` 판이어야 하고, `app.` 같은 하위 도메인은 따로 승인받는다). ⑤ 계정 인증(KYC/KYB)을 계정 관리자가 마친다 — 개인 정보와 사업 정보, 사이트 주소, 판매할 것의 설명이 필요하고 서류를 더 요구받을 수 있다. ⑥ 정산(payout) 정보를 넣는다.
  - 기다림: 인증은 보통 하루 안에 끝나지만 지역과 상품에 따라 며칠이 걸릴 수 있다고 Paddle 문서가 쓴다. 도메인 승인 날수는 문서에 없다. 그래서 인증을 샌드박스 연동보다 먼저 시작하고, 도메인 승인은 인증과 나란히 신청한다. 인증의 자동 심사는 승인된 도메인이 하나 이상 있어야 진행된다.
  - 사이트가 갖춰야 하는 것(Paddle 인증 준비 항목): 약관·개인정보처리방침·환불 정책 쪽이 공개돼 있고, 사이트의 가격이 Paddle 상품 가격과 맞고, 홈에서 닿는 연락처(이메일 또는 문의 폼)가 있다.
- 설정: 호스팅 환경 변수(대시보드 또는 `vercel env add <이름>` 표준 입력)에 `LF_MODE`(live 배포는 live), `PADDLE_API_KEY`, `PADDLE_WEBHOOK_SECRET`, 오버레이를 쓰면 `PADDLE_CLIENT_TOKEN`, `NEXT_PUBLIC_APP_URL`(배포 주소), `CRON_SECRET`(결제 Cron 용, 없으면 Cron 경로가 401)을 넣는다. 데이터베이스 값(`DATABASE_URL`)은 `G-db`, 메일 값(`RESEND_API_KEY`·`EMAIL_FROM`)은 `G-email` 에서 넣은 것을 쓴다. 가입·결제 폼의 봇 방어 값 `TURNSTILE_SECRET_KEY`·`TURNSTILE_SITE_KEY` 는 이미 넣은 값을 재사용한다.
- 설정: `lib/launch/paddle-plans.ts` 에 요금제와 Paddle 가격 id 를 적는다. 비어 있으면 결제가 열리지 않는다(`unknown_plan`). 체험이 있는 요금제는 체험 없는 가격 id 와 체험 있는 가격 id 를 둘 다 적는다.
- 설정: `vercel.json` 에 `/api/cron/billing` Cron 을 더한다(저장소 안내의 스케줄은 매시 정각).
- 설정: 실결제 스위치 `LF_PADDLE_LIVE` 는 샌드박스에서 비워 둔다. 값을 1 로 넣어야 실결제(production)로 간다 — 실결제 계정·키·알림 대상이 모두 준비된 뒤 사이트 주인만 넣는다.
- 설정: 실결제에서 Paddle 의 결제 복구 메일(Retain)을 켰다면 `LF_PAYMENT_FAILED_EMAIL` 을 off 로 둔다(결제 실패 안내가 두 번 나가지 않게). EU 결제 국가에 팔지 정하는 값은 `LF_EU_SALES`(기본 열림, off 로 닫는다).
- 설정: 결제 시작은 언제나 청약철회 제한 동의 체크를 요구한다. 끄는 설정은 없다.
- 확인: 샌드박스에서 가입 → 요금제 선택 → Paddle 시험 카드(공식 문서의 시험 카드)로 결제 → Paddle 대시보드의 알림 기록에 성공(2xx)이 찍힘 → 사이트의 결제 관리 화면에 구독 상태가 보임. 실카드는 쓰지 않는다. 실결제 전환 뒤에는 Paddle 문서의 전체 점검표(도메인 승인·인증 완료)를 지난 뒤 100% 할인 거래로 한 번 시험한다.
- 막힘: 서명 오류(401) → 알림 대상을 다시 만들어 비밀 키가 바뀐 경우가 많다, 호스팅의 `PADDLE_WEBHOOK_SECRET` 을 새 값으로. 샌드박스 키로 실결제 쪽을 부르면 거절된다(샌드박스·실결제 키를 섞지 않는다). 알림이 안 들어옴 → 서버가 5초 안에 2xx 를 줘야 하고, 아니면 Paddle 이 다시 보낸다(Paddle 문서: 샌드박스는 약 2분 안에 3번, 실결제는 약 2일 동안 최대 60번). 배포 미리보기에 호스팅 보호 인증이 걸려 있으면 Paddle 알림도 막힌다. 실결제 결제창이 안 열림 → 도메인 승인 전이거나 기본 결제 링크의 호스트가 승인된 도메인과 다르다.
- 출처: Paddle 개발자 문서(developer.paddle.com) — Sandbox 안내, 출시 점검표(Set up checklist), Authentication(API 키·클라이언트 토큰), Notification destinations·Respond to webhooks·Signature verification, Default payment link, 상품·가격 만들기, Verifications. 저장소: `.env.example`, `features/outcomes.yaml`, `registry/feature-billing-paddle` 의 설치 안내, `packages/billing-paddle`.

## G-booking — 예약

- 등록: 없음. 알림 받을 메일 하나(`BOOKING_OWNER_EMAIL`, 이메일 형식이 아니면 부팅이 멈춘다).
- 설정: `lib/launch/booking-config.ts` — 서비스·영업시간·휴무일·수용량·취소 마감·안내 시각. `mode` `"instant"`(접수 즉시 확정) · `"request"`(관리 화면 예약 구획에서 확정 필요).
- Cron: `vercel.json` 에 `/api/cron/booking`, `*/30 * * * *`. 시작 전 안내·보유 기간 지난 예약 파기. `CRON_SECRET` 없으면 401.
- 폼: 숨은 입력 `cf-turnstile-response` · `idempotencyKey`(폼을 열 때 생성).
- 확인: `env:check` 경고 없음 → `/book` 이 폼을 그림 → 시험 예약 → 대표 메일 수신.
- 예약금: 서비스에 `deposit`(원)을 적고 `feature-booking-deposit`(결제 중개 `payments-kr` 필요)을 붙인다. 접수 → 결제 대기(자리는 `depositPolicy.holdMinutes`, 기본 30분 붙들림) → 결제하면 확정. 같은 Cron 이 기한 지난 결제 대기를 닫아 자리를 푼다. 취소하면 마감 안은 전액 환불(마감 뒤는 `laterRefundPercent`), 대표(관리 화면)가 취소하면 시각과 상관없이 전액 환불(`ownerCancelRefundPercent`, 기본 100, 0~100으로 바꿀 수 있다), 환불이 실패하면 예약은 취소되지 않고 다시 시도할 수 있다. 금액·결제 번호는 5년 보유. 한계: 새로고침하면 결제를 이어 하지 못한다(다시 예약하거나 기한까지 기다린다).

(이 장은 같은 파일의 공유 절도 함께 읽어요: booking-notify-push)

## G-inquiry — 문의 접수

- 왜 필요한가: 문의 폼으로 들어온 글을 데이터베이스에 저장하고 대표 메일로 알려 주려면, 알림 받을 메일 주소와 메일 보내기(`G-email`)·데이터베이스(`G-db`)가 먼저 되어 있어야 한다.
- 준비물: 알림을 받을 대표 메일 주소(개인정보라 저장소에 적지 않는다), 끝낸 `G-db`·`G-email`, 호스팅 환경 변수 화면.
- 등록: 없음. 외부 서비스 계정은 새로 필요 없다. 봇 방어 키(`TURNSTILE_SECRET_KEY`·`TURNSTILE_SITE_KEY`)는 보안 장 `G-security` 에서 만든 값을 그대로 쓴다.
- 설정: 호스팅 환경 변수(대시보드 또는 `vercel env add <이름>` 표준 입력)에 `INQUIRY_OWNER_EMAIL`(알림 받을 대표 메일, 이메일 형식이 아니면 켜질 때 멈춘다)을 넣는다. `LF_BUSINESS_EMAIL` 로 대신하지 않는다 — 그것은 바닥글에 공개하는 표시 주소다. 함께 필요한 값은 이미 정한 것을 쓴다: 데이터베이스 `DATABASE_URL`, 봇 방어 `TURNSTILE_SECRET_KEY`·`TURNSTILE_SITE_KEY`, Cron 용 `CRON_SECRET`, 메일 `RESEND_API_KEY`·`EMAIL_FROM`, 인증 항목이 함께 설치되므로 `BETTER_AUTH_SECRET`.
- 설정: 문의 폼에는 숨은 입력 둘이 필요하다 — Turnstile 토큰 `cf-turnstile-response` 와, 폼을 열 때 만든 `idempotencyKey`.
- 설정: `lib/launch/support.ts` 에서 첫 응답 약속(`responseTime`), 접수 확인 메일(`receipt`), 사람이 읽는 문의 메일 주소(`email`)를 정한다. 지킬 수 있는 응답 시간만 적는다(없으면 null). 접수 확인 메일은 방문자가 적은 주소로 나가므로 요청 제한과 Turnstile 이 남용을 막는 유일한 장치다.
- 설정: `vercel.json` 에 `/api/cron/inquiry` Cron 을 더한다(저장소 안내의 스케줄은 하루 한 번). 일반 문의는 30일, 불만·분쟁 문의는 3년 보유 뒤 이 Cron 이 파기한다. `CRON_SECRET` 이 없으면 Cron 경로는 401 이다.
- 설정: 데이터베이스 마이그레이션을 한 번 돌린다(`DATABASE_URL` 은 직접 연결 주소로 `node db/migrate.mjs`).
- 확인: 배포 환경에서 문의 쪽에 폼이 그려지는지(`data-inquiry="enabled"`) → 시험 문의 하나 보내기 → 대표 메일에 알림 도착 → (접수 확인 메일을 켰다면) 폼에 적은 주소로 확인 메일 도착.
- 막힘: 폼 대신 안내만 보임 → live 에서 `INQUIRY_OWNER_EMAIL` 이 없어서 문의 창구만 꺼진 것이다(사이트는 켜진다, 접수는 거절되고 받은 척 저장하지 않는다. 쪽의 `data-inquiry` 표지가 `disabled`). 접수가 거절됨 → Turnstile 토큰 또는 요청 제한 확인. 알림 메일이 안 옴 → 메일 장의 `EMAIL_FROM` 인증 상태와 스팸함. 같은 요청이 두 번 저장됨 → 폼을 열 때 `idempotencyKey` 를 만드는지 확인.
- 출처: 저장소만 읽었다 — `.env.example`, `features/outcomes.yaml`, `registry/feature-inquiry` 의 설치 안내와 `support.ts`. 외부 서비스 문서는 이 장에서 읽지 않았다(외부 등록 없음).

## G-notify — 카카오 알림톡 · 문자 (Solapi)

- 등록 1 — Solapi 계정(본인인증). 개인 계정은 하루 한도·발신번호 수가 작다. 기업 계정이 넉넉하다.
- 등록 2 — 발신번호(문자·대체발송에 필수): 사전 등록 번호만 발송 가능. 서류(통신서비스 이용증명원, 재직증명서 등), 검토 영업일 1~3일. → `SOLAPI_SENDER`.
- 등록 3 — API Key/Secret 발급 → `SOLAPI_API_KEY`·`SOLAPI_API_SECRET`. (콘솔 메뉴 위치는 버전마다 다르다. 이 글은 확인하지 않았다.)
- 등록 4 — 알림톡(선택): 카카오톡 채널 개설 → 비즈니스 심사(사업자등록증 또는 고유번호증, 대표자 인증, 며칠) → 채널 공개·검색 허용 ON, 고객센터 연락처 입력 → Solapi 에 채널 연동 → 채널 id `KA01PF…` → `SOLAPI_KAKAO_PFID`.
- 등록 5 — 알림톡 템플릿 심사: Solapi 에서 등록·검수 요청, 카카오 심사 보통 영업일 1~3일. **정보성 문구만 통과**(광고·결제 유도 문구는 반려·소명 대상). 요청한 템플릿은 수정 불가(오탈자도) — 새로 등록한다. 발송 이력이 1년 없으면 휴면. 통과 id → `lib/launch/notify-kr-config.ts` 의 `NOTIFY_TEMPLATES.alimtalkId`. 심사 전·중에는 문자로 나간다.
- 광고성 문자(`purpose: "marketing"`): 채널 동의(`feature-consents`) + 21시~다음날 8시 금지 + 「(광고)」 머리 + 무료수신거부 번호(`MARKETING_OPT_OUT_NUMBER`). 하나라도 어긋나면 `skipped` 와 이유. 발송 화면은 제품 몫.
- 확인: 전화번호로 시험 예약 → 문자/알림톡 수신 → Solapi 발송 내역(보관 12개월). 메일만 오면 `SOLAPI_*` 셋 중 빈 값.

## G-payments-kr — 국내 결제 (PortOne V2)

- 왜 필요한가: 상점이 한국 카드·간편결제로 돈을 받으려면 PortOne 계정과 결제 채널, 서버용 비밀, 웹훅 비밀이 있어야 한다. 값 넷 중 하나라도 없으면 상점만 꺼지고 사이트의 다른 부분은 켜진 채로 남는다.
- 준비물: 사업자등록·통신판매업 신고·PG 가맹을 다루는 `G-biz-kr` 를 먼저 끝낸 상태. 올라간 사이트의 주소(웹훅 주소와 복귀 주소에 쓴다), 데이터베이스(`G-db`)와 호스팅(`G-hosting`)이 끝난 상태. 호스팅 환경 변수에 값을 넣을 수 있는 계정.
- 등록 1 — PortOne 에 가입한다. 공식 안내에 따르면 가입은 별도 계약 없이 무료이고, 가입 뒤 인증 메일을 확인해야 로그인된다. 실결제를 받으려면 콘솔의 전자결제 신청에서 사업자 정보를 입력하고 쓸 PG·결제수단을 신청한다. 이 신청의 소요 일수는 [확인 안 됨]이다(PG 연락과 카드사 심사 기간은 `G-biz-kr` 의 PG 가맹 항목을 본다). 전자결제를 신청하기 전에도 테스트 채널로 먼저 시험할 수 있다.
- 등록 2 — 상점 아이디(store id)를 확인한다. 가입하면 대표 상점이 자동으로 만들어지고, 상점마다 고유한 값이 있다 → `NEXT_PUBLIC_PORTONE_STORE_ID`. 결제창을 열 때 쓰는 공개 값이다.
- 등록 3 — 결제 채널을 만든다. 콘솔의 채널 관리에서 연동 모드(테스트 또는 실연동)와 결제대행사(PG), 결제 모듈을 고른다. 테스트 채널은 공용 테스트 상점 아이디를 고르거나 직접 받은 테스트 아이디를 넣는다. 실연동 채널은 PG 와 계약한 뒤 받은 상점 아이디와 추가 정보를 넣는다. 채널을 만들면 얻는 채널 키 → `NEXT_PUBLIC_PORTONE_CHANNEL_KEY`(공개 값). 간편결제(카카오페이·네이버페이·토스페이)는 PG·사별 계약과 심사가 따로 필요하다.
- 등록 4 — 콘솔의 식별코드·API Keys 쪽에서 V2 API Secret 을 발급한다. 발급과 삭제는 소유자·관리자 계정만 할 수 있고, 값은 발급 직후에만 보인다(잊으면 새로 발급한다). 서버에서만 쓰고 브라우저에 노출하지 않는다 → `PORTONE_API_SECRET`. 보이는 그 자리에서 호스팅 환경 변수에 넣는다.
- 등록 5 — 웹훅을 등록한다. 콘솔의 결제알림(웹훅) 관리 쪽에서 웹훅 버전은 결제모듈 V2, 설정 모드는 테스트 또는 실연동 중 하나를 고른다. 모드마다 주소와 웹훅 시크릿을 따로 둘 수 있다. 주소는 `https://<도메인>/api/webhooks/portone`, 발급받은 웹훅 시크릿(`whsec_…`) → `PORTONE_WEBHOOK_SECRET`. 주소를 바꿨으면 저장한 뒤에 시험 알림을 보낸다(저장하지 않고 시험하면 이전에 저장한 주소로 간다).
- 설정: 위 넷을 호스팅 환경 변수에 넣는다(대시보드 또는 `vercel env add <이름>` 표준 입력). `NEXT_PUBLIC_*` 둘은 빌드 때 번들에 들어가므로 바꾸면 다시 배포한다. 값은 채팅·저장소·로그에 쓰지 않는다.
- 설정: 실제 돈이 오가는 배포는 `LF_MODE` 를 live 로 둔다. mock 에서는 PortOne 값이 있어도 모의 결제를 쓴다.
- 설정: 결제 대기 주문을 정리하는 Cron 이 돌려면 `CRON_SECRET` 이 호스팅에 있어야 한다(`G-hosting` 에서 정한 값을 그대로 쓴다). 없으면 만료 정리가 안 돈다.
- 테스트와 실결제: 연동 모드는 채널마다, 웹훅은 모드마다 따로다. 테스트 채널로 먼저 통과시킨 뒤 실연동 채널의 채널 키와 실연동 모드의 웹훅 주소·시크릿으로 바꿔 다시 배포한다. API Secret 이 모드별로 따로인지는 [확인 안 됨]이고, 테스트 채널이 실제 돈을 청구하지 않는다는 PortOne 쪽 명시 문장도 [확인 안 됨]이다 — 첫 시험은 소액으로 한다.
- 결제 흐름: 서버가 주문을 만들고 금액을 정한다(가격의 정본은 서버 상품표, 클라이언트 금액은 읽지 않는다) → 브라우저가 `requestPayment`(통화 `KRW`) → 모바일은 `redirectUrl` 로 돌아온다 → 서버가 `paymentId` 로 PortOne 을 **다시 조회**한다.
- 검증 위치(`packages/commerce` `confirmPayment`): 상태가 `PAID` 여야 하고 `amount.total` 과 통화(KRW)가 주문 행과 같아야 한다. 아직 대기면 `payment_pending`(재시도 가능), 금액·통화가 다르면 그 결제를 환불하고 `payment_amount_mismatch`. 리디렉션 반환과 웹훅이 같은 `confirmPayment` 를 부르고 주문 행의 조건부 갱신을 이긴 쪽만 확정·메일·계측(`purchase`)을 한다 — 몇 번 불러도 한 번이다. PortOne 문서도 브라우저 완료와 웹훅 도착 순서는 보장하지 않는다고 하므로 두 길 모두 재조회로 확정한다.
- 웹훅(`handleWebhook`): 원문 본문(`request.text()`)으로 서명 확인(Standard Webhooks, 시간 허용 5분) → `webhook-id` 중복 제거 → `Transaction.Paid` 만 주문을 움직이고 `paymentId` 로 재조회한다. 응답: 400 서명·헤더·본문 오류 / 200 처리·중복·쓰지 않는 이벤트 / 503 아직 결제 완료로 안 보임(기록을 되돌려 PortOne 이 다시 보낸다) / 404 상점 꺼짐·mock. 실패·취소 이벤트는 받아 두기만 한다. PortOne 문서에 따르면 연결·읽기 제한 시간은 각각 30초이고, 실패한 웹훅은 최대 5번까지 다시 보내며 간격은 지수로 늘어난다(문서 표기 0 → 1 → 4 → 16 → 64 → 256분, 무작위 지연 포함).
- Cron 만료: 결제 대기 주문은 30분(`holdMinutes`) 뒤 만료. `vercel.json` 의 `/api/cron/commerce`, `*/10 * * * *`(한 번에 최대 100건). 만료 대상이 공급자에서 이미 `PAID` 면 취소하지 않고 확정한다(웹훅을 놓친 경우). 아니면 취소하고 재고를 돌려준다.
- 취소·환불: 결제 전 주문은 취소+재고 반환. 결제 후(`paid`·`preparing`)는 PortOne 환불이 성공해야 `refunded` 가 된다 — 실패하면 상태 그대로 `refund_failed`(재시도 가능). 준비가 시작된 주문은 환불해도 재고를 되돌리지 않는다. 취소된 주문에 늦게 들어온 결제는 전액 환불한다. SDK 0.19.0 은 `Idempotency-Key` 를 보내지 않아 멱등은 우리 쪽 상태 전이가 지킨다.
- 확인: ① 테스트 채널로 소액 결제 1건 → 주문 `paid` + 확인 메일 ② 그 주문 취소/환불 → `refunded` + 재고 복구 ③ 웹훅 설정 쪽의 시험 알림으로 200 응답을 확인한다. 실제 결제 알림의 발송 내역 화면이 있는지는 [확인 안 됨] ④ 결제창만 열고 닫아 30분 뒤 Cron 이 정리하는지.
- 막힘: ① 상점 액션이 `provider_unavailable` → PortOne 값 넷 중 빠진 이름이 있다(`NEXT_PUBLIC_*` 는 바꾼 뒤 재배포). ② 웹훅이 400 → 시크릿이 다른 모드의 것이거나 시계가 5분 넘게 어긋났다. ③ 결제는 됐는데 주문이 대기로 남음 → 웹훅 주소 미등록, 기다리면 재조회·Cron 이 확정한다. 증상 표 전체는 이 파일의 4절이다.
- 법적 고지: 총액 표시·청약철회 문구 등 PortOne 쪽 문구는 [확인 안 됨] — 사이트 법정 쪽(`/terms`·`/refund`)은 대표 검토 몫.
- 출처: PortOne 개발자 문서(developers.portone.io) — 결제 연동 준비하기, 연동 정보(채널·식별코드·웹훅 관리), 웹훅 연동하기, 퀵 가이드, PortOne REST API V2. 저장소: `.env.example`, `packages/payments-kr`, `packages/commerce`.

(이 장은 같은 파일의 공유 절도 함께 읽어요: commerce-site-owner)

## G-commerce — 상점 (장바구니 · 주문 · 재고)

- 왜 필요한가: 사이트가 상품을 직접 팔려면 상품표·배송비·재고를 정하고 결제(`G-payments-kr`)를 이어야 한다. 이 모듈이 장바구니·주문·재고 확보·주문 확인 메일을 맡는다.
- 준비물: 결제가 연결된 상태(`G-payments-kr`), 데이터베이스(`G-db`), 메일(`G-email`). 팔 상품의 이름·가격·재고 제한·배송비.
- 등록: 없음. 외부 서비스는 위 `G-payments-kr` 가 전부다.
- 설정: 상품과 배송비를 코드 설정 `lib/launch/catalog.ts` 의 `PRODUCTS`·`SHIPPING` 에 적는다. 가격의 정본이 여기다. 재고 제한도 여기서 정한다(`stock: null` 은 무제한). 주문이 진행되는 동안에는 가격을 바꾸지 않는다.
- 설정: 주문 확인 메일은 메일 장(`G-email`)의 설정으로 나간다. 보내는 주소는 `EMAIL_FROM` 이다. 메일이 안 가도 주문은 확정된다.
- 주문 한 바퀴: 담기 → 장바구니 → 배송지 → `placeOrder`(재고 30분 확보, 결제 세션 생성) → 결제 → `confirmPayment` → 주문 내역. `placeOrder`·`cancelOrder` 는 사람 확인(`confirmed: true`) 없이는 상태를 바꾸지 않는다(`confirmation_required`, 오류 아님). 한 사람이 동시에 가질 수 있는 결제 대기 주문 수에 한도가 있다(`too_many_pending`).
- 쓰기 액션은 요청 제한을 먼저 지나고, 대리 로그인 중에는 읽기만 된다.
- 화면과 처리: 공개 상품 목록 쪽(`/products`, 카드는 `/cart?add=<상품 id>` 로 간다), 장바구니·결제·내 주문 화면, 관리 화면의 주문·재고 구획(`G-admin`)이 있다. 계정을 지우면 결제된 주문은 소비자를 알아볼 키가 없는 가명 결제 기록으로 60개월 남고, 끝난 주문의 배송지는 바로 비워진다. 내 정보 내려받기에는 본인 주문이 들어간다. 아직 없는 것: 품절 표지(웹 팩토리 블록에 없다), 진짜 PortOne 결제창 한 바퀴(키가 있는 환경에서만 확인할 수 있다).
- 확인: `commerceEnabled()` 가 true(live 는 PortOne 값 넷, mock 은 항상) → 서버 액션 `catalog` 가 상품을 돌려줌 → 소액 시험 결제 → 주문 `paid` → 메일.
- 막힘: ① 만료·취소했는데 재고가 안 돌아옴 → Cron 이 안 돈다(`CRON_SECRET` 없음). 준비 중 이후의 환불은 재고를 되돌리지 않는 것이 의도다. ② `too_many_pending` → 결제 대기 주문이 한도에 닿았다. 30분 뒤 만료되거나 취소하면 풀린다. ③ `confirmation_required` → 오류가 아니라 사람 확인 대기다.
- 출처: 이 저장소의 `.env.example`, `packages/commerce`, `docs/qa/p3a-commerce.md`. 외부 서비스 사실은 `G-payments-kr` 에 있다.

## G-push — 웹 푸시 (VAPID)

- 등록: 없음(외부 계정 불필요). `npx web-push@3.6.7 generate-vapid-keys` 로 키 한 쌍.
- 설정: `VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY`(비밀) · `VAPID_SUBJECT`(`mailto:` 또는 `https://`). 하나라도 없거나 틀리면 푸시만 꺼진다. 키를 바꾸면 기존 구독이 못 쓰인다 — 바꾸지 않는다.
- 조건: HTTPS 필수(localhost 예외). iOS 는 홈 화면에 추가한 앱만 수신. 로그인한 사용자만(비로그인은 메일·알림톡). 권한은 사용자가 단추를 누를 때만 묻는다.
- 확인: 로그인 → 푸시 단추 → 허용 → 서버에서 `(await push()).sendToUser(userId, { title, body })` → 기기에 알림. 단추가 없으면 VAPID 셋을 본다.
- 막힘: 푸시 서비스 401·403 = 우리 VAPID 설정 문제(구독은 안 지운다). 404·410 = 폐기된 기기(자동 삭제). 보낼 시점은 제품 코드가 정한다.

(이 장은 같은 파일의 공유 절도 함께 읽어요: booking-notify-push)

## G-search — 사이트 검색

- 등록: 없음. 별도 검색 서비스 없이 Postgres `ILIKE` 로 찾는다(한국어 부분 문자열 가능, 제목 일치 가중).
- 색인: `content/search-index.json` 의 문서 목록. 형식이 틀리면 아무것도 바꾸지 않는다(옛 색인 유지).
- 첫 배포 뒤: Cron 이 돌기 전에는 비어 있다 — 한 번 직접 부른다: `curl -H "Authorization: Bearer $CRON_SECRET" https://<사이트>/api/cron/search`.
- 확인: 검색 상자에 문서 제목의 낱말 → 결과와 강조 범위. 빈 질의는 오류가 아니라 빈 결과.
- 주의: 문서가 수만 건을 넘으면 `ILIKE` 가 느려진다. 그때 별도 검색 서비스를 따로 검토한다(이 모듈 범위 밖).

## G-security — 요청 제한 · 봇 확인 · Cron 비밀

- 왜: 공개 폼이 봇과 반복 요청에 뚫리지 않게 하고, Cron 경로를 아무나 부르지 못하게 하려고 봇 확인 키 한 쌍과 Cron 비밀 하나를 정한다.
- 준비물: 환경 변수를 넣을 호스팅 화면(`G-hosting`), 요청 제한 기록을 저장할 DB 연결 `DATABASE_URL`(값은 `G-db` 에서 정한다), Cloudflare 계정.
- 등록 1 — Cloudflare 계정을 만든다(이미 있으면 그대로). Turnstile 은 Cloudflare 대시보드 안의 서비스다. 무료 플랜은 검증 요청이 무제한이고 위젯 수와 위젯당 호스트 수에 한도가 있다.
- 등록 2 — Turnstile 위젯을 하나 만든다. 이름, 위젯을 쓸 호스트(사이트 도메인), 위젯 모드(Managed · Non-Interactive · Invisible 중 하나)를 정한다. 호스트는 도메인 이름만 쓴다 — 스킴·포트·경로·와일드카드는 받지 않고, 루트 도메인을 적으면 그 하위 도메인도 포함된다. 만들고 나면 사이트 키와 비밀 키가 나온다 → `TURNSTILE_SITE_KEY`(공개) · `TURNSTILE_SECRET_KEY`(비밀, 안전하게 보관).
- 설정: `TURNSTILE_SITE_KEY` — 위젯을 그릴 때 쓰는 공개 값. live 에서 필수다.
- 설정: `TURNSTILE_SECRET_KEY` — 서버가 토큰을 검증할 때 쓰는 비밀. live 에서 필수이고 없으면 만들 때 던진다. 브라우저에 보내지 않는다. 개발 mock 에서는 키 없이 통과한다.
- 설정: 위젯은 폼 안에 숨은 입력 `cf-turnstile-response` 를 넣고 토큰을 서버가 검증한다. 토큰은 만든 뒤 5분 안에 한 번만 검증된다. 사용자가 늦게 제출하면 위젯을 새로 고쳐야 한다. 서버 검증은 키트가 한다.
- 설정: `CRON_SECRET` — 값은 16자 이상의 무작위 문자열로 직접 만든다(Vercel 은 비밀번호 생성기를 권한다). 호스팅 프로젝트의 환경 변수 `CRON_SECRET` 으로 넣으면 Vercel 이 Cron 을 부를 때 `Authorization` 머리에 `Bearer` 와 함께 자동으로 붙인다. 키트의 Cron 경로는 이 값이 없거나 다르면 401 로 거절하고, 값이 없을 때 열어 두지 않는다. 값은 채팅에 쓰지 않는다.
- 설정: 환경 변수를 바꾸면 이미 있는 배포에는 적용되지 않고 새 배포부터 적용된다. Turnstile 비밀 키를 바꿀 때는 Cloudflare 가 두 시간 동안 옛 키와 새 키를 둘 다 받아 주니 그 사이에 바꾼다.
- 설정: 요청 제한은 경로 이름별 규칙이다(기본 `signUp` · `signIn` · `passwordReset` · `inquiry` · `checkoutStart`). 한도를 넘으면 429 와 `Retry-After` 로 답한다. 새 경로는 규칙을 더해야 하고, 규칙 없는 이름은 던진다(한도 없이 통과하지 않는다). 폼을 두 번 보내도 한 번만 처리하는 멱등 키 표도 같은 DB 를 쓴다.
- 설정: 정리 Cron `/api/cron/security`(하루 한 번, 템플릿 `vercel.json` 에 이미 있다)가 지난 제한 기록과 멱등 키를 지운다. 이 Cron 도 `CRON_SECRET` 이 없으면 401 이다.
- 설정: 요청 제한은 요청 머리의 IP 로 센다. 기본은 어떤 머리도 믿지 않아서 IP 를 못 찾으면 경로마다 공용 통 하나로 센다(정상 방문자도 함께 막힐 수 있다). Vercel 에서는 자동으로 알맞은 머리를 믿는다. 다른 호스트라면 신뢰 프록시 종류, 앞단이 덮어쓰는 클라이언트 IP 머리 하나, 프록시 주소 중 하나를 환경 변수로 정한다 — 이름은 보안 항목 설치 안내 7번에 있다.
- 확인: `npm run env:check -- --vercel` 경고 없음 → 새로 배포 → 가입이나 문의 폼에 위젯이 보임 → 제출이 통과함. Cron 은 `curl -H "Authorization: Bearer $CRON_SECRET" https://<사이트>/api/cron/security` 가 200, 머리 없이 부르면 401.
- 막힘: 폼이 봇 확인 실패로 거절한다 → 토큰이 5분 지났거나 이미 한 번 검증된 토큰이다(`timeout-or-duplicate`). 위젯을 새로 고쳐 다시 제출한다.
- 막힘: 위젯이 안 뜨거나 거절된다 → 위젯의 호스트 목록에 사이트 도메인(미리보기 배포의 도메인 포함)이 없다. 목록을 고친다. 템플릿은 Turnstile 에 필요한 CSP 출처를 이미 넣어 두었다.
- 막힘: 모든 Cron 이 401 → 배포에 `CRON_SECRET` 이 없다. 넣은 뒤 새로 배포한다.
- 막힘: 정상 방문자가 429 를 만난다 → IP 를 못 찾아 공용 통으로 세는 중일 수 있다. Vercel 이 아닌 호스트라면 위의 IP 설정을 본다.
- 출처: Cloudflare Turnstile 공식 문서 — 위젯 만들기, 호스트 관리, 클라이언트 렌더링, 서버 검증(siteverify), 비밀 키 교체, 플랜 안내(developers.cloudflare.com). Vercel 문서 — Cron 보안(`CRON_SECRET`), 환경 변수(vercel.com). 이 저장소의 `.env.example`과 보안 항목 설치 안내.

## G-consent — 마케팅 수신 동의

- 왜: 광고성 정보는 받는 사람이 미리 동의한 채널로만 보낼 수 있어서, 채널별 동의·철회 이력과 수신거부·2년 재확인을 이 기능이 맡는다.
- 준비물: 로그인(`G-auth`)과 메일(`G-email`)이 먼저 켜져 있어야 한다. 동의 이력은 로그인한 사용자 기준이고, 통지·재확인 메일은 메일 항목으로 나간다. 비밀 값 `CRON_SECRET` 은 `G-security` 에서 만든다.
- 등록: 없음. 새 외부 계정이 필요 없다.
- 설정: 동의 상태는 채널별(이메일·문자·카카오·푸시)이고 기본은 모두 거부다. 사용자가 사람이 확인한 입력으로 바꿀 때만 바뀌며, 바뀔 때마다 이력이 한 줄 남는다. 설정 화면은 제품이 만든다(현재 값 읽기와 바꾸기 서버 액션을 부른다).
- 설정: 사업자 정보 `LF_BUSINESS_NAME` · `LF_BUSINESS_EMAIL` · `LF_BUSINESS_PHONE` · `LF_BUSINESS_ADDRESS` 가 **모두** 있어야 광고성 메일이 만들어진다. 하나라도 비면 광고성 메일은 던지고 나가지 않는다(거래 메일은 영향 없음). 값은 메일 장(`G-email`)에서 정한다.
- 설정: `BETTER_AUTH_SECRET` — 로그인 없이 누르는 수신거부·계속 받기 링크의 서명 비밀을 이 값에서 만든다. 바꾸면 이미 나간 메일의 링크가 열리지 않는다. 값은 인증 장(`G-auth`)에서 정한다.
- 설정: `CRON_SECRET` 과 Cron `/api/cron/consents`(하루 한 번, 템플릿 `vercel.json` 에 이미 있다). 비밀이 없으면 이 경로는 401 이라 2년 재확인 메일이 나가지 않는다.
- 설정: `LF_MARKETING_NIGHT_GUARD` — 비우면 켜져서 한국 시각 21시~다음 날 8시에는 광고성 메일 보내기를 아침으로 미룬다. `off` 로 끈다. 전자우편은 법상 야간 동의 대상이 아니라서, 법이 요구하는 점검이 아니라 보수적인 기본값이다.
- 동작: 광고성 메일은 키트의 광고 메일 보내기 함수로만 보낸다. 보내기 전에 채널 동의·재확인·야간을 점검하고, 메일러가 제목 「(광고)」·전송자 표시·한글·영문 수신거부 안내·로그인 없는 수신거부 링크·`List-Unsubscribe` 머리를 단다. 광고 메일을 보내는 화면과 문구는 제품이 만든다.
- 동작: 수신거부 링크는 누르면 바로 철회하고 이력을 남긴다. 이미 철회한 사람이 다시 누르거나 메일 보안 프로그램이 미리 열어도 통지가 되풀이되지 않는다. 철회한 사람은 「계속 받기」 링크로 되살아나지 않는다 — 다시 동의하려면 설정 화면에서 직접 한다.
- 동작: 동의·거부·철회를 표시할 때마다(같은 값을 다시 표시해도) 그 사람의 메일로 처리 결과 통지가 나간다. 보내기가 실패해도 설정 저장은 되돌리지 않는다. 실패한 통지는 발신함에 남고 알림 Cron 이 간격을 늘려 다시 보낸다. 이메일이 없는 계정(카카오 등)은 통지 메일을 보낼 수 없으니 그런 계정에 마케팅을 켜기 전에 다른 통지 수단을 정한다. 통지에 쓰는 전송자 명칭은 설정 파일의 제품 이름이다 — 법적 상호로 바꾼다.
- 동작: 2년 재확인 — 동의한 지 2년이 지난 이메일 수신자에게 전송자·동의 사실과 날짜·계속 받기/수신거부 링크가 든 메일을 한 통씩 보낸다. 답이 없는 사람에게는 계속 보낸다(규칙에 끊는다는 문구가 없다 — 법무 확인 필요). 재확인 메일을 아직 못 보낸 2년 넘은 동의에는 보내지 않는다.
- 동작: 가입 때의 약관·개인정보·만 14세 동의 기록은 인증 항목이 하고(그 기록은 DB 트리거가 수정과 비우기를 막는다), 이 기능은 그 이력을 이어 쓴다. 개인정보 수집·국외 이전 고지 표의 데이터도 이 기능이 만든다(화면은 제품 몫).
- 확인: 로그인 → 설정 화면에서 이메일 수신 켜기 → 처리 결과 통지 메일 도착 → 메일 안 수신거부 링크를 로그아웃 상태로 열기 → 철회 → 통지 메일 다시 도착. 재확인 Cron 은 `curl -H "Authorization: Bearer $CRON_SECRET" https://<사이트>/api/cron/consents` 로 한 번 불러 건수 응답(보낼 것·보냄·건너뜀·실패)을 본다.
- 막힘: 광고 메일이 안 나간다 → 이유를 본다. 동의 없음 · 재확인 대기(2년 넘었는데 재확인 메일 전) · 야간(다시 시도할 시각이 같이 온다). 사업자 정보가 비었으면 이유가 아니라 오류로 던진다.
- 막힘: 통지 메일이 안 온다 → 메일 항목(`G-email`) 설정을 본다. 이메일이 없는 계정이면 보낼 수 없다.
- 막힘: 재확인 Cron 이 401 → 배포에 `CRON_SECRET` 이 없다. 환경 변수는 새 배포부터 적용된다.
- 막힘: 수신거부 링크가 안 열린다 → 링크를 만든 뒤 `BETTER_AUTH_SECRET` 을 바꿨다.
- 출처: 이 저장소의 동의 기능(패키지와 설치 안내)·`.env.example`. 법 근거는 저장소의 법무 메모를 따르며 이 글은 확인하지 않았다 [확인 안 됨]. Vercel Cron 보안 문서(vercel.com).

## G-newsletter — 뉴스레터 구독

- 등록: 새 계정 없음. `G-email` 의 Resend 계정과 인증한 도메인(`EMAIL_FROM`)이 먼저 있어야 확인 메일이 나간다. 봇 확인은 Turnstile.
- 동의: 체크박스는 **미리 체크하지 않는다**(정보통신망법 제50조). 문구를 고치면 `NEWSLETTER_CONSENT_VERSION` 판을 올린다 — 동의한 때의 판이 구독자 행에 남는다.
- 흐름: 신청 → 확인 메일(이중 동의) → 링크 확인 → 구독 시작 안내 메일. 이미 구독 중인 주소도 같은 응답(존재 여부를 알리지 않는다).
- 링크: 확인·수신거부 링크는 `BETTER_AUTH_SECRET` 에서 파생한 서명으로 만든다. 메일 보안 프로그램이 링크를 미리 열면 확인이 사람 손 전에 끝날 수 있다 — 필요하면 `/email` 쪽이 단추를 보이고 POST 하게 한다(항목 문서 4항).
- 보내기: 이 모듈의 일이 아니다. 서비스의 구독자 목록(`unsubscribeUrl` 포함)을 보내는 도구에 넘기고, 보내는 도구가 메일마다 본문 링크와 `List-Unsubscribe` 헤더(원클릭)에 수신거부 주소를 단다. 제목 「(광고)」 · 전송자 표시 · 사업자 정보는 보내는 쪽 몫이다.
- 확인: 시험 주소로 신청 → 확인 메일 수신 → 링크 → 구독 완료 → 같은 주소로 다시 신청해도 같은 화면. 메일이 안 오면 `G-email`(키·도메인 인증)을 본다.

## G-reviews — 후기 · 상품 문의

- 등록: 없음.
- 설정: 대상은 제품이 정한다 — `subjectType`(소문자·숫자·`-_`)과 `subjectId`. 게시 방식은 `REVIEWS_MODERATION`(`after` 바로 게시 후 검토 · `before` 검토 후 게시).
- 폼: 숨은 입력 `cf-turnstile-response` · `idempotencyKey`. 후기는 로그인한 사람만 한 대상에 한 번, 질문은 로그인 없이도 된다.
- 관리: 관리 화면 구획 `reviews`(`/admin/reviews`) — 검토 목록·판매자 답변·승인·숨김(사유 필수 — 구획이 고정 사유를 싣는다, 관리 기록 한 줄)·다시 보이기. 예전 서버 액션(`answerReview`·`setReviewStatus`·`listReviewsForModeration`)은 구획이 서비스를 직접 부르게 되며 없어졌다. 권한은 세션의 사용자 행(소유자·관리자)으로 정한다.

- 확인: 시험 후기 제출 → 목록·별점 요약에 반영 → 숨김 → 목록에서 빠짐.

## G-storage — 파일 올리기 (S3 호환 저장소)

- 등록 1 — 저장소 계정: AWS S3 · Cloudflare R2 · MinIO(직접 운영) 중 하나. 요금·무료 구간은 서비스마다 다르다(이 글은 확인하지 않았다).
- 등록 2 — 버킷 하나. 비공개 종류(`attachment`)는 버킷을 공개하지 않는다(짧은 서명 주소로만 읽는다).
- 등록 3 — 키: 이 버킷의 객체 쓰기·읽기·삭제만 허용한 전용 키. → `STORAGE_ACCESS_KEY_ID` · `STORAGE_SECRET_ACCESS_KEY`. 계정 전체 키를 쓰지 않는다.
- 등록 4 — CORS(브라우저가 직접 PUT 한다): 허용 출처에 사이트 주소, 메서드 `PUT`(공개 읽기면 `GET` 도), 머리 `content-type`.
- 등록 5 — 공개 읽기(avatar · image): 버킷 또는 공개 도메인이 읽기 공개여야 한다. CDN·공개 도메인을 쓰면 `STORAGE_PUBLIC_BASE_URL`.
- 설정: 다섯 필수(`STORAGE_ENDPOINT` · `BUCKET` · `REGION` · `ACCESS_KEY_ID` · `SECRET_ACCESS_KEY`). R2·MinIO 는 `STORAGE_PATH_STYLE=true`. 종류별 상한·형식은 정책 표(`packages/storage/src/policy.ts`): avatar 2MB(로그인 필요) · image 5MB · attachment 10MB(비공개, 보유 365일).
- 탈퇴: 전체 템플릿에서는 탈퇴한 사람의 파일이 장부에서 「지울 때」로 당겨지고 파기 직후와 파일 Cron 에서 객체가 지워진다.
- 확인: 로그인 → 작은 이미지 올리기 → 티켓 → 저장소에 객체가 생김 → 끝내기 → 주소로 보임. 올리기 단추가 안 나오거나 503 이면 STORAGE 다섯 개 중 빈 값을 본다. 브라우저 콘솔에 CORS 오류가 나면 등록 4.
- 막힘: `storage.notUploaded`(끝내기가 먼저 불림) → 업로드 PUT 이 실패한 것(CORS·서명 시계 어긋남). 속인 크기·형식은 객체가 지워지고 거절된다.

## 3. 더 싼 방법이 있는지 (확인용 자리)


- 국내 결제에는 PortOne 밖의 방법도 있다: 다른 국내 PG·결제 중개사, 링크로 받는 결제, 계좌이체만 받기 등. 수수료·요금은 이 글에 적지 않는다(바뀌고, 확인하지 않았다).
- 플러그인은 「더 싼 방법 없나요?」 질문을 받으면 이 모듈의 결제 자리(`PaymentGateway`)에 무엇이 들어갈 수 있는지와 확인할 항목만 안내한다. 비교 수치는 사업자가 각 공급자 공식 요금 안내에서 직접 확인한다.

## 2. Cron


`vercel.json` 에 이미 있다(템플릿 기준). 설치한 앱에 직접 더할 때만 아래를 넣는다. 모두 `CRON_SECRET` 이 없으면 401.

| 경로 | 일정 | 하는 일 |
|---|---|---|
| `/api/cron/search` | `20 4 * * *` | 색인 파일(`content/search-index.json`)로 종류별 색인을 바꾼다 |
| `/api/cron/newsletter` | `30 4 * * *` | 확인 안 한 신청(14일)·수신거부 기록(1년)을 지운다. 구독 중인 사람은 안 지운다 |
| `/api/cron/storage` | `40 4 * * *` | 끝내지 않은 올리기(24시간)·보유 기간이 지난 파일·탈퇴한 사람의 파일 객체를 지운다 |
